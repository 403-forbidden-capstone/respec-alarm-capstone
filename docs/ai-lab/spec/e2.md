- e1-b2의 다른 칸 변화(준비시간 오류 0 → 2, 할 일 3 → 5)는 대화 2곳씩의 뒤바뀜(OK ↔ null)으로 e1-b1에서는 반대 방향(준비시간 2.0 → 0.5 / 2.5)이라 잡음으로 봄.

## 5. 단계 2 — 언제 뽑나 (한 턴 5초 예산)

### 5.1 설정

- 5초 예산 = 사용자가 말을 마친 뒤 AI가 말하기 시작할 때까지. 지금은 추출 → 서버 → T1이 직렬.
- E1 대화 b1의 AI 답 자리 **179곳**(사용자 말 뒤)에서 T1.v1.3을 같은 화면 · 같은 대화로 다시 부르되 **T1이 보는 서버 처리 결과만** 바꿈:

| 보기 | T1이 보는 처리 결과 | 뜻 |
|---|---|---|
| C0 | 사용자 말 j까지 | 지금 방식 (추출이 끝난 뒤 T1) · 기준 |
| L1 | j−1까지 | (b) T1 먼저, 추출은 뒤에서 — 한 턴 늦음 |
| L0 | 하나도 없음 | (d) 대화 중엔 서버가 아무것도 안 함 |
| N0 | j까지, T1 생각 끔 | 운영처럼 지연을 줄인 설정에서의 지연 · 품질 |

- 처리 결과는 저장된 추출을 **지금 스텁**(DENIED 줄 포함)에 다시 넣어 만듦. 한 자리만 바꾸는 반사실 재생이라 앞 AI 턴 글은 원래 대화(C0 흐름)에서 온 것 — L1 · L0에서 "아까 저장했다고 한 말은…" 같은 말이 나오면 이 영향이 섞임.
- 지연은 실행마다 따로, 동시 4로, 다른 모델 실행과 안 겹치게 잼 (단계 1의 끝 한 번 추출만 동시 8). T1은 E1 설정(effort low, 생각 요약 켬), T2는 medium(기본 생각), T2F는 low. 같은 자리끼리 짝지어 더한 값이라 서로 다른 실행의 호출을 이어 붙인 것.

### 5.2 처리 결과가 바로 필요했던 턴 (b1)

| 필요했던 것 | 자리 수 |

- 79곳 중 **다음 AI 턴이 있는 곳 71곳**(한 턴 늦게라도 전할 수 있음), 8곳(10%)은 대화가 거기서 끝나 아무도 안 전함. 확인 필요 18곳은 모두 다음 턴이 있음 → 한 턴 늦으면 **새 일정마다 한 턴 더**.

### 5.4 (c) 빠른 추출 T2F — 속도 · 정확도

T2F = 서버가 대화 중에 움직이는 칸만 뽑는 새 프롬프트·스키마 (`prompts/T2F.v*.md`, `schemas/extract-fast.v1.json`: appointments · alarm_changes · fact_feedback · prep_adjustment · safety_flag; 중요도 변경은 appointments[ref].importance). 사용자 말 243개(b1)마다 그 말까지의 대화로 뽑아 턴별 정답으로 채점(t2.ts 턴별 모드와 같은 규칙). 비교 기준 `quo` = E1 대화 중 실제로 돈 T2.v1(medium, 생각 요약 켬)을 같은 정답으로 다시 채점한 것.

| 방식 | 구성 | 서버를 움직이는 것만 F1 (오류 · 지어냄) | 지어냄 | 안전 실패 | 지연 p50 / p95 | 출력 토큰 | 호출당 $ |
|---|---|---|---|---|---|---|---|
| quo | T2.v1 전체 · medium · 생각 요약 | 0.965 (15 · 17) | 26 | 0 | 7.4 / 10.9초 | — | — |
| v2t | T2.v2 전체 · medium (오늘 다시 잼) | 0.967 (14 · 17) | 21 | 0 | 5.7 / 9.1초 | 1,173 | 0.00079 |
| T2F.v0 | 5칸 · low · 생각 끔 | 0.915 (38 · 27) | 57 | 7 | 1.5 / 2.5초 | 171 | 0.00026 |
| T2F.v0-stt | v0 + 받아쓰기 글 읽기 블록 | 0.914 (39 · 31) | 58 | 10 | 1.5 / 2.5초 | 173 | 0.00027 |
| T2F.v1 | v0 + 기록 · 위험 신호 줄 강화 | 0.926 (33 · 25) | 55 | 0 | 1.5 / 2.3초 | 171 | 0.00026 |

- 서버를 움직이는 것만 = 약속 · 알람 변경 · 준비시간 · 기록 **정정(CORRECTED) · 부정(DENIED)**. 기록 확인(CONFIRMED) · 애매함(UNCLEAR)은 처리 결과 줄을 안 만들므로 T2F에서 빼고 끝 한 번 추출에 맡김(T2F.v2 · v2-a만 그렇게 뽑게 함). 그래서 이 두 판의 '5칸 F1'(0.59 · 0.51)은 일부러 낮은 값이라 비교에 안 씀. 위 표는 모든 판에 같은 방식(확인 · 애매함 항목을 정답 · 출력에서 뺌)으로 다시 채점한 값.
- 생각 없이(low · 끔) 빠르게 뽑으면 **기록 확인 · 정정에서 지어냄**(말 안 한 기록 CONFIRMED · UNCLEAR 31+12), **"오늘 열두 시쯤 잘 거야"를 어젯밤 취침 정정으로**, **"준비물 챙기느라 더 걸릴 듯"을 준비시간 늘리기로**, 안전 표시 헛경보(7~10턴)가 나옴. 줄을 더하는 것(v1, v2)으로는 안 고쳐지고 effort를 올려도(v1-m) 안 고쳐짐 — **생각이 있어야 고쳐짐**(v2 → v2-a, 오류 39 → 12).
- 확인한 새 묶음 e1-b2 (T2F.v2-a): 서버를 움직이는 것만 F1 **0.982 (오류 7 · 지어냄 1)**, quo 0.967 (13 · 14). 지연 2.1 / 4.3초. 안전 · 출력 실패 0.
- T1이 바로 알아야 하는 처리 결과를 T2F.v2-a가 찾았나 (사용자 말 243개 · 240개, 'quo의 처리 결과'를 기준으로): b1 둘 다 있음 71 · 놓침 9 · 헛울림 1 / b2 67 · 10 · 2. **놓침의 대부분은 준비물 · 할 일 저장 줄**(b1 9건 중 8건, b2 10건 중 7건 — T2F가 todos를 안 뽑아서) → todos를 T2F에 더하는 것이 다음 시험(미검증). 나머지는 b1 1건(기록 정정이 앞 턴에 이미 반영돼 두 번째 줄이 안 생김, 해 없음) · b2 3건(준비시간 가감 + 할 일 섞인 1: s3-dev-015, 지난 시각 일정 거절 1: s3-dev-033, 앞과 같은 반영 중복 1: s3-dev-005). 헛울림은 b1 1건(s3-dev-044 일정 변경 확인 대기), b2 2건(s3-dev-032 "열두 시 반쯤 잘 거야"를 어젯밤 취침 정정으로, s3-dev-061 다른 사람 알람 끄기 거절).
- 약속 오류 4건은 quo와 T2F가 똑같음: 턴별 정답이 '현재 상태'를 요구해서, 앞 턴에 낸 약속(지난 시각 일정 등)을 다음 턴에 다시 안 내면 FN으로 셈 — 서버는 앞에서 이미 받았으니 해가 없는 채점 규칙 탓.
- 끝 한 번 전체 추출(T2.v2)을 대화 뒤에 더해도 **중복이 생기지 않음**: 만든 약속 9개가 E1 흐름과 같고(더 만듦 0 · 빠짐 0, b1 · b2), 끝 추출이 새로 낸 저장됨 · 확인 필요 줄은 b1 0 · 1 / b2 0 · 0. 끝 한 번 추출의 F1 자체는 4.2의 v2 값(0.960, b2 0.944) — 턴마다 뽑은 것에 끌리지 않음. 참고로 E1 대화에서 마지막 턴별 추출 F1은 0.930.

### 5.5 방식별 비교와 권고 (b1 179자리, 같은 자리끼리 짝지어 더함)

| 방식 | 구성 | 기다림 p50 / p95 (초) | 5초 넘는 턴 | 처리 결과를 제때 | 정확도 (서버를 움직이는 것) |
|---|---|---|---|---|---|
| (a) 지금 | T2.v1 → 서버 → T1 (E1 설정) | **11.1 / 15.6** | 176/179 | 필요한 자리 79/79 | F1 0.965 |
| (a′) 같은 방식, 오늘 다시 잼 | T2.v2 한 턴 → T1 | 9.7 / 14.0 | 174/179 | 79/79 | 0.967 |
| (b) T1 먼저, 추출 뒤에서 | T1 (한 턴 늦은 화면) | 4.2 / 6.6 | 59/179 | 거의 못 전함 (저장됨 1/61 · 확인 0/18) | 추출은 그대로, 한 턴 늦게 반영 |
| (c) 빠른 추출 → 서버 → T1 | T2F.v2-a + T1 | 5.9 / 8.8 | 122/179 | 71/80 (준비물 · 할 일 빼고 거의 다) | **0.972** |
| (d) 끝에만 추출 | T1 (처리 결과 없음) | 4.5 / 6.7 | 64/179 | 0 (대화 뒤 카드로만) | 전체 추출 F1 0.960 |
| **(e) T2F ∥ T1 미리, 처리할 게 있으면 T1 다시** | T1(처리할 것 없다고 가정) 동시에 T2F; 서버가 "처리할 것 없음"이면 그 답, 있으면 T2F 뒤에 T1 한 번 더 | **4.2 / 8.8** (처리할 게 없는 턴 3.6 / 5.0, 있는 턴 6.4 / 9.8) | 64/179 | (c)와 같음 | (c)와 같음 |

- (e)는 직접 끝까지 돌린 것이 아니라 **짝지은 호출 지연 · 품질로 계산**함. 처리할 게 없는 턴에서 미리 부른 T1은 (c)에서 T2F가 '없음'이라고 한 뒤 부른 T1과 **입력이 같은 글**(서버 처리 결과에 '사용자 말 j 뒤: 바뀐 것 없음' 줄까지 미리 넣어 부름) → 그 턴의 품질 = C0.
- (e) 비용: 턴당 T2F $0.0003 + T1 $0.0004 (+ 처리할 게 있는 44% 턴에 T1 한 번 더 ≈ $0.0002) ≈ $0.0009. 지금은 T2 $0.0008 + T1 $0.0004 = $0.0012. 대화 끝에 T2.v2 한 번($0.0008)을 더해도 대화당(3.4턴) 지금 $0.0041 ≈ (e) $0.0039.
- **권고 (e) + 끝 전체 추출**. 사용자가 느끼는 것: 대부분의 턴(56%)은 3.6초, 뭔가 저장 · 확인할 게 있는 턴(44%)은 6.4초쯤 걸리지만 바로 그 턴에 "저장했어요 / 저장할까요?"가 나옴. 5초 안에 못 들어오는 턴이 지금 98%에서 36%.
- 5초를 더 줄이려면 T1 자체가 3.7초인 것이 병목(생각을 끄면 1.8초지만 규칙 어김이 4배) → 운영 모델(Gemini)의 T1 지연을 먼저 재야 함. 처리할 게 있는 턴에는 서버가 짧은 맞장구("네, 확인해 볼게요")를 미리 읽어 줄 수 있음(미시험).

## 6. 단계 3 — 이유 태그(T3)가 받아쓰기 글에서도 되나

- 입력: data/t3.json의 dev 문장 66개(시험용 44개는 안 읽음), T3.v1 그대로. 원문(잡음 없음) 대 받아쓰기 흉내 mid · high. 2번씩 (원문은 같은 글 2번, mid · high는 반복마다 다른 잡음 시드). 채팅 말(ㅇㅇ · ㅋㅋ · ㅠㅠ)이 든 문장 17개는 음성으로 안 나올 말이라 '말로 할 수 있는 문장 49개'를 먼저 봄.
- **같은 날 다시 잰 원문 점수가 예전 dev 실행(97.0%)보다 낮음**(93.2%) — 경계 문장 몇 개가 하루 사이에 뒤바뀜(r16 '버스 놓침' 등). 그래서 비교는 이 실행 안의 원문과 함.

| 입력 | 말로 할 수 있는 49문장: 정확도 (1번째 · 2번째) | 평균 | 경계 사례 | dev 전체 66문장 평균 |

## 7. 아직 모르는 것 · 한계

- **Gemini에서는 하나도 확인 안 됨.** T2F의 '적응형 생각'은 Claude 설정이고 Gemini의 생각 수준 · 지연 · responseSchema 지킴은 모름. 지연 숫자(T2F 2.0초, T1 3.7초)도 Haiku 값.
- 받아쓰기는 흉내(mid). 높은 잡음에서도 규칙이 효과 없음을 봤지만 진짜 구글 받아쓰기가 더 이상한 틀림(숫자를 통째로 빠뜨림 등)을 내면 다름.
- 방식 (e)는 호출 지연 · 품질을 짝지어 **계산한 것**. 끝까지 도는 앱 흐름(T2F · T1 동시 호출, 재호출, TTS)으로는 안 돌려 봄. 가상 유저가 AI 답에 반응하는 대화도 새로 안 만듦(반사실 재생).
- T2F.v2-a 프롬프트는 e1-b1의 오류를 보고 3번 고친 것이라(v0 → v1 → v2 → v2-a) b1 숫자는 낙관적. e1-b2에서 한 번 확인(0.982)했고 시험용 사람 · 새 시나리오로는 안 돌림.
- T2F가 놓치는 준비물 · 할 일 저장 줄(b1 8건/243턴, b2 7건/240턴)은 todos를 T2F에 더해 보지 않아 미검증 (예산 때문에 못 함).
- PRESENTATION 한 줄(v2)은 e1-b2에서 지어낸 할 일 2건(발표 준비물 · 옷)을 불렀음. 이유 태그 이득은 PRESENTATION 정답이 든 대화(b1 3개 × 2번, b2 3개)에 몰려 있음 — 정답 항목 수가 작음.
- 정답(gold)은 Sonnet 1회 검수(10/13 사용자 30건 확인 전). 같은 입력을 2번 돌린 F1이 같게 나온 것(0.944 · 0.944)은 우연일 수 있어 폭 바닥(0.015)을 둠.
- 'E1 때 설정'의 T2 지연(7.4초)은 생각 요약을 받는 설정이라 오늘 같은 프롬프트로 다시 잰 5.7초(T2.v2 한 턴)보다 큼. 두 값을 같이 적음.
- 시험용 사람 4명 · 시험용 T3 문장은 안 씀 — 최종 확인 때.
