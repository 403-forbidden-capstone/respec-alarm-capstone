# 실험정리 — 앱 지점별 AI 프롬프트 실험 (v3, 음성 받아쓰기 기준)

> **D7 (10/13 팀 결정): 음성 대화는 실시간(Gemini Live 단말 직결, 목소리도 Gemini Live).** 이 실험은 1턴(받아쓰기 글 → 답 · 추출) 전제라 실시간 경로에서 그대로 쓰이는지는 `인계.md` 'D7 영향' 표 참고.
> 실험 하나가 끝날 때마다 한 장씩 채움. 모양은 [보고서_설계.md](보고서_설계.md) 2절, 계획은 [실험계획_v3.md](실험계획_v3.md).
> 모든 실험은 Claude Haiku 5.5로 했고 운영 모델 Gemini에서는 확인 안 됨.

용어 (처음 한 번만)
- 받아쓰기(STT) = 폰이 마이크로 들은 말을 글자로 바꿔 주는 기능. 앱은 안드로이드 기본(구글) 음성 인식을 가정함. 실제 엔진이 아니라 규칙으로 흉내 낸 잡음을 씀.
- T0 받아쓰기 정리 · T1 대화 답 · T2 저장할 것 뽑기. 번호는 앱 지점 이름표.
- F1 = 말한 것 중 맞게 뽑은 비율과, 뽑은 것 중 맞는 비율을 합친 점수 (1.0이 만점).
- 정답(gold) = 검수자가 '사용자가 실제로 한 말'(하려는 말)을 다시 읽고 만든 표.
- 감지 오류 기록 = 앱이 자동으로 잰 기록(기상 · 출발 · 도착)인데 실제와 다른 것. 사용자가 "그건 아니에요"라고 고쳐 말해야 앱이 배움.
- 서버 질문 = 서버가 정해 주는 물음(예: 지각 이유). 돌아보기(REFLECT) = "오늘 하루 어땠어요?"처럼 하루를 돌아보는 물음. 이른 마무리 = 사용자가 끝내자는 신호를 안 줬는데 AI가 먼저 끝냄.

## E0. 받아쓰기 정리 (T0)

**한 줄 결론**: 받아쓰기를 정리하는 단계를 따로 두지 않아도 됨 — 정리 없이 넣은 추출 점수(F1 0.925)가 하려는 말을 그대로 넣은 점수(0.927)와 사실상 같아서 정리가 올릴 여지가 없고, 정리하면 뜻이 1.5~2%(추정) 바뀌고 한 턴이 1.2초 느려짐.

**왜 했나**
- 사용자는 말로 하고 폰이 글자로 바꿔 주는데, 그 글에는 숫자가 '일곱 시 반'과 '7시 30분'으로 섞이고, 군말 · 말 바꾸기 · 비슷한 소리 오류가 있음.
- "이 글을 LLM이 한 번 정리해 주면 뒤 단계(저장할 것 뽑기 · 답)가 나아지나?"를 보려고 했음. 정리한 글은 사용자에게 안 보이고, 잘 안 들린 곳은 표시해서 T1이 자연스럽게 되묻게 하려는 계획이었음.

**누구로 해 봤나** — 개발용 8명, 한 명당 9대화 (유형 24가지 × 3 = 72대화, 사용자 말 202개). 시험용 4명은 안 씀.

**대화로 보면** — 같은 사용자 말 하나에 정리 방식별로 어떻게 달라졌나 (실제 기록, 정리 판 이름: v0 = 이름 목록 없이, ctx = 앱의 일정 · 장소 · 사람 이름 목록을 같이 줌, 고친 판 ctx01)

예 1. 이름이 틀리게 적힌 경우 (민준 p04, 대화 s3-dev-071, 사용자 말 1)

```
AI        오늘은 14시 1분에 일어나 15시 조별 발표에 6분 늦게 도착했고, 18시엔 로봇 동아리에 갔어요. 틀린 기록이 있으면 말해 주세요.
하려던 말   음 그 기상 시각은 틀렸어요. 실제로는 한 시 오십일 분에 일어났어요. 나머지는 맞아요. 아 그리고 내일 열역학이 아홉 시에서 열한 시로 바뀌었어요.
받아쓰기   음 기상 시각은 틀렸어요 실제로는 1시 51분에 일어났어요 나머지는 맞아요 아 그리고 내일 열력학이 9시에서 열한 시로 바뀌었어요
정리 v0    … 내일 열력학이 9시에서 11시로 바뀌었어요.   ← 이름은 그대로, 숫자만 통일. [표시: 열력학 — '열역학'의 오인식일 수 있음]
정리 ctx   … 그리고 내일 열역학이 9시에서 11시로 바뀌었어요.   ← 목록 이름으로 되살림. [표시: '1시 51분' 오전/오후 — 헛짚음]
정리 ctx01 … 그리고 내일 열역학이 9시에서 11시로 바뀌었어요.   ← 표시 없이 되살림
T2 추출    (받아쓰기 그대로 · v0 · ctx · 합친 판 · 하려던 말 모두 같음)
           약속 a3 열역학 10/14 11:00 (시각 변경) · 기록 f2 정정 13:51 · 나머지 기록 확인
```
- 정리는 이름을 되살렸지만(ctx) 추출 결과는 안 달라짐. T2가 일정표에서 '열역학'(a3)을 찾아 짝지음.
- T1의 답(받아쓰기 그대로 받은 경우): "기상 시각을 13시 51분으로 고쳐 저장했어요. 내일 열역학을 11시로 옮기는 것도 저장할까요?" — 틀린 이름을 말하지 않고 조용히 맞춰 말함.

예 2. 말 바꾸기 + 이름 소리 틀림 (준혁 p08, s3-dev-021, 사용자 말 1)

```
하려던 말   … 그런데 내일 계량경제학이 아홉 시 아 아니 열 시로 바뀌었어요.
받아쓰기   … 그런데 내일 계략경제학이 아홉 시 아 아니 10시로 바뀌었어요.
정리 v0    … 그런데 내일 계략경제학이 10시로 바뀌었어요.   ← 말 바꾸기 정리됨, 이름은 그대로 [표시: 계략경제학]
정리 ctx   … 그런데 내일 계량경제학이 10시로 바뀌었어요.   ← 둘 다 됨 [표시: 목록 이름으로 고쳤지만 확실치 않음]
T2 추출    (모든 입력 같음) 약속 a1 계량경제학 10/12 10:00
```
- 받아쓰기 그대로여도 T2는 '아홉 시 아 아니 10시' 중 마지막 값을 씀.

예 3. 정리가 숫자를 틀리게 바꾼 경우 (도현 p02, s3-dev-004, 사용자 말 1)

```
하려던 말   어 그냥 알람 끄고 다시 잤어. 한 십일 분쯤 더.
받아쓰기   어 그냥 알람 끄고 다시 잤어 한 십일 분쯤 더        ← 받아쓰기는 맞음
정리 v0    그냥 알람 끄고 다시 잤어. 한 10분쯤 더.        ← 11분이 10분으로 (틀림)
정리 ctx   그냥 알람 끄고 다시 잤어. 한 10분쯤 더.        ← 같은 실수
정리 ctx01 그냥 알람 끄고 다시 잤어. 11분쯤 더.            ← 고쳐짐 ('한'은 빠짐)
T2 추출    (모두 같음) 이유 OVERSLEPT (늦잠)
```
- 이런 숫자 실수가 143개 중 1~2개 (v0 · ctx 2개, 고친 판 1개 — 다른 말). T2가 분을 안 쓰는 대화라 점수는 안 변했지만, 분을 저장하는 대화였다면 틀린 값이 저장됨.
- '오십일 분 → 50분'(s3-dev-065)도 같은 실수.

예 4. 표시를 받은 T1이 되묻는 경우 (지우 p05, s3-dev-011, 사용자 말 1)

```
하려던 말   네, 기상 시각은 맞아요. 아, 준비물은 학생증이랑 컴퓨터용 사인펜 챙길 거예요.
받아쓰기   네 기상 시각은 맞아요 아 준비물은 헉생증이랑 컴퓨터용 사인펜 챙길 거예요
정리 ctx01 … 준비물은 학생증이랑 컴퓨터용 사인펜 챙길 거예요.   [표시: 헉생증 — '학생증'으로 고쳤으나 확실하지 않음]
서버가 T1에 전하는 처리 결과  되물을 것: 받아쓰기 확인: '헉생증'이(가) 제대로 들렸는지 (…)
T1 (받아쓰기 그대로)  좋아요, 학생증이랑 컴퓨터용 사인펜 챙기는 걸로 저장해 두었어요. …
T1 (표시 받음)       좋아요, 학생증이랑 컴퓨터용 사인펜 챙기는 걸로 저장해 뒀어요. 혹시 '헉생증'이 아니라 '학생증'이 맞는지 확인해 줄래요?
```
- 표시를 받으면 T1이 시킨 대로 물음 1개로 되묻음. 그러나 '학생증'은 뻔해서 사용자는 어색할 수 있음 — 표시의 기준이 너무 후함.
- 정말 모르는 말에서는 필요한 되묻기도 나옴: "장소는 씬촌역이 맞는지 신촌역인지 한 번만 확인할게요" (s3-dev-043).

**결과** (대화 72개 · 사용자 말 202개 · 정리 호출 말마다 1번)

| 보는 것 | 받아쓰기 그대로 | 정리 v0 | 정리 ctx | 고친 판 ctx01 |
|---|---|---|---|---|
| 숫자 143개 중 맞게 살린 | 143 | 141 | 141 | 142 |
| 앱이 아는 이름이 틀린 7번 중 되살린 | 0 | 1 | **6** | 5 |
| 새 일정 이름이 틀린 11번 중 되살린 | 0 | 4 | 6 | 6 |
| 말 바꾸기 3번 중 앞 값을 지운 | 0 | 3 | 3 | 2 |
| 뜻이 바뀐 말 (표본 30개 중) | — | 4 | 3 | 0 |
| 하려는 말에 없는 새 낱말이 든 말 (202 중) | 0 | 5 | 8 | 4 |
| 추출 F1 (대화 72 × 2번) | **0.925** | 0.917 | 0.925 | 0.919 |
| 한 턴에 더해지는 시간 p50 / p95 | 0 | 1.2초 / 2.0초 | 1.2초 / 1.9초 | 1.1초 / 1.9초 |

- 하려는 말을 그대로 넣은 추출 F1이 0.927 → 정리가 올릴 수 있는 최대치가 0.002. 같은 입력을 두 번 돌려도 0.926 → 0.923으로 흔들려서(대화 8/72가 다르게 나옴) 이 차이는 구분 안 됨.
- 잡음을 high로 올려도(틀린 새 이름 21곳) 받아쓰기 그대로의 F1은 0.923. 정리는 틀린 새 이름 21곳 중 15~17곳을 고치지만 점수는 0.914~0.924로 같음.
- 정리가 숫자를 가끔 틀리고(143개 중 1~2개), 잘린 말을 짐작으로 채우고('안녕히' → '안녕히 계세요'), 고친 판은 짧은 답에서 지시문을 따라 적기도 함 (202말 중 1~2건, 서버가 길이 · 지시 낱말로 막아야 함).
- 표시: 정리가 짚은 곳의 3분의 2는 헛짚음(v0 34개 중 23). 고친 판은 26개 중 13이 실제 잡음. 그래도 받아쓰기가 틀린 34곳 중 13곳만 짚음.
- 표시를 T1에 되물을 것으로 넘기면, 실제로 틀린 31곳 중 되묻는 곳이 8 → 17. 대신 잡음이 없는데 표시 때문에 물은 곳이 8곳 중 3.
- 돈은 말 한 번에 $0.00007 (Haiku, 생각 끔). 시간이 비용.

**그래서 프롬프트에 넣을 말**
- 이 지점(①)은 **호출하지 않음**. T2 · T1 프롬프트에 받아쓰기 안내 문단도 넣지 않음 (넣은 판도 0.918로 같았고 문단이 쓰인 흔적이 없음).
- 나중에 정리 호출이 필요해지면 [프롬프트카드/01-받아쓰기정리.md](프롬프트카드/01-받아쓰기정리.md)의 T0.v0.1-ctx를 쓰고, 핵심은 3문장:
  - "단 뜻과 낱말은 바꾸지 마: 사용자가 하지 않은 말은 절대 더하지 마."
  - "글이 끝에서 잘린 듯해도 짐작으로 완성하지 마. 잘린 그대로 두고 uncertain에 적어."
  - "한자어 수는 글자 그대로 더해서 읽어: 십일 = 10 + 1 = 11."
- 서버가 막을 것: 정리본이 받아쓰기보다 1.5배+10자 넘게 길거나 절반 미만이면, 또는 '위 글을 정리해' · '처리:' 같은 낱말이 있으면 받아쓰기 글로 되돌림. 위험한 말 감지는 정리 전 받아쓰기 글에 한 번 더.

**아직 모르는 것**
- 진짜 구글 받아쓰기의 틀리는 모양 (흉내 두 수준만 봄). 이보다 훨씬 나쁘면 결론이 바뀔 수 있음 → 앱 개발 중 실제 받아쓰기 30건쯤 모아 다시 보는 게 가장 확실함.
- Gemini에서의 동작 전부 (생각 끄기 · 숫자 읽기 · 추론이 글에 새는 실패).
- 정리한 글로 대화가 이어졌을 때 T1이 다르게 묻는 흐름 (기준 대화는 받아쓰기 그대로 만든 것). E1에서 '모르는 곳 되묻기' 켠 판과 끈 판을 사람 평가로 비교해야 함.
- 표본이 작은 곳: 말 바꾸기 4말, 새 이름 11곳, 뜻 판정 30말.
- 가상 유저 SIM.v3.1: 한자어 시각('칠 시 육 분')이 10말에 나옴, 수다쟁이 2명 18대화 중 5대화가 스스로 '지어냄'이라 보고.
- 라운드 1 숫자(저장 · 약속 말투 검사)는 옛 검사기로 센 것. 새 검사기로 다시 세면 라운드 1 T1 변형 대화는 걸리는 AI 턴이 10~37% 늘어남 (예: fv1-c1 244턴 중 30 → 41, freeze-v0은 그대로 55).

## E1. 자기 전 · 기상 후 대화 답 (T1)

**한 줄 결론**: AI가 읽어 주는 기록을 서버가 골라 주고(확인할 기록), 시각을 서버가 '오후 6시 30분'처럼 말로 바꿔 넘기고, 첫마디를 기록 확인만으로 줄이면 — 앱이 잘못 잰 기록을 사용자가 고쳐 말한 비율이 39개 중 16개(41%) → 78개 중 59개(76%)가 됨. 대가는 대화 +0.4턴 · 한 번 +0.4초. 서버 질문부터 시작하면(C) 11개 중 0개.

**왜 했나**
- 자동으로 잰 기록(기상 · 출발 · 도착)은 틀릴 때가 있음: 알람을 끄고 누워 폰을 보면 기상 시각이 10~15분 이르고, 쓰레기 버리러 나가면 '출발'로 잡힘. 사용자가 고쳐 말해야 앱이 배우는데, AI가 그 기록을 읽어 주지 않으면 고칠 기회가 없음.
- 라운드 1(타이핑 대화)에서 확인할 기록을 서버가 고르면 1/6 → 6/6으로 오르고, 흐름 프롬프트(첫마디는 기록 확인만 · 서버 질문은 다음 턴 · 마무리 전에 돌아보기 1번)가 더 알아내되 길어졌음. 사용자가 말로 하는 설정(받아쓰기 글 · 8명 72대화)에서 이 묶음이 그대로 되는지 보려 했음.
- 비교: A = 예전 판 (E0 기준 대화 그대로), B = 새 묶음, C = B를 서버 질문 먼저로 시작.

**누구로 해 봤나** — 개발용 8명, E0와 같은 72대화 (B는 2번, A는 오류 있는 30대화를 한 번 더). 시험용 4명은 안 씀. 이 실험에서 눈여겨볼 3명:

| 이름 | 나이 · 학과 · 통학 | 말투 | 앱 기록이 어디서 틀리나 |
|---|---|---|---|
| 서윤 p01 | 21 · 경영학 · 지하철 환승 65분 | 차분한 존댓말, 틀린 기록은 정확히 고침 | 알람 끄고 **누워서 폰 10~15분** → 기상 시각이 이름 (s3-dev-037: 앱 09:02, 실제 09:12) |
| 하은 p03 | 20 · 시각디자인 · 집 50분 | 수다쟁이 반말, 감탄 많음 | 누워서 폰 15~30분 → 기상 · 출발 시각 틀림 (s3-dev-005: 기상 11:26 → 11:51) |
| 도현 p02 | 23 · 컴공 · 기숙사 10분 | 짧고 무심한 반말, "응 맞아" | 아침에 편의점 잠깐 다녀옴 → **가짜 출발** (s3-dev-029) |

나머지 5명과 사람 카드 전체 = `spec/v3-setup.md` 2절. 사람별 숫자 = [spec/e1.md](spec/e1.md) 4.6.

**대화로 보면** — 같은 시나리오(같은 사람 · 같은 하루)에서 A(예전 판)와 B(새 묶음). 받아쓰기가 하려던 말과 다른 곳만 표시. 실제 기록.

예 1. 기상 · 출발 기록이 둘 다 틀린 날 (하은 p03, s3-dev-005, 33분 지각)

```
A  AI: 오늘 색채학에 33분 늦었어요. 준비가 예상보다 10분 더 걸렸고, 미루기도 3번 있었어요. 이유가 있었는지 골라 주실래요?
        ← 파생 기록(지각 · 준비 초과) + 서버 질문을 첫 턴에 섞음
   사용자: 헐 대박 맞아 진짜 늦었어. 아 그니까 알람을 세 번이나 미루다가 늦게 일어났어. …
   AI: 알람을 세 번 미루다 보면 아침이 많이 급했을 것 같아요. …
        → 기상 11:26(진짜 11:51) · 출발 12:51(진짜 12:40)은 말하지 않음, 그대로 저장

B  AI: 오늘 기록이에요. 기상은 오전 11시 26분, 출발은 낮 12시 51분, 도착은 오후 1시 33분이었어요. 틀린 게 있으면 말해 주세요.
        ← 서버가 고른 세 기록만 · 시각을 말로
   사용자(하려던 말): 아 잠깐, 기상은 열한 시 이십육 분이 아니라 열한 시 오십일 분이었어. 그리고 출발도 열두 시 오십일 분 아니고 열두 시 사십 분이야. …
   AI: 고쳐 주셔서 고마워요. 기상은 오전 11시 50분, 출발은 낮 12시 40분으로 저장했어요. 오늘 하루는 어땠어요?
        ← 서버의 '저장됨' 뒤에 '저장했어요' · 돌아보기 1번
   사용자: 아 맞다, 기상 열한 시 오십 분이라고 저장했다고? 나 열한 시 오십일 분이었는데 …
   AI: … 기상은 오전 11시 51분으로 저장했어요, …
```
- 눈여겨볼 곳: 추출(T2)이 '오십일 분'을 50분으로 저장했는데, AI가 저장한 값을 되읽어 준 덕에 사용자가 바로잡음.

예 2. 알람 끄고 누워 폰을 본 날 (서윤 p01, s3-dev-037, 앱 기상 09:02 → 실제 09:12)

```
A  AI: 오늘 재무관리 수업에 22분 늦으셨어요. 미루기는 3번 있었고, 어젯밤 취침은 23:34였어요. 틀린 게 있으면 말씀해 주세요.
        ← 기상 기록을 읽지 않음 · 24시간 숫자
   사용자: 네, 미루기 세 번 맞고요, 어젯밤 취침 시각도 맞아요. 지각은 이십이 분이라고 하셨는데, 음, 그것도 맞아요.
   AI: 네, 기록이 맞다니 다행이에요. 내일은 9시 마케팅원론이 있으니 6시 50분 기상 알람을 맞춰 두었어요, 지금 대화는 여기서 마칠까요?
        ← 서버가 안 한 알람 설정을 '맞춰 두었어요'라고 말함 (규칙 어김)

B  AI: 오늘은 오전 9시 2분에 일어나서 오전 9시 40분에 출발했고, 오전 10시 52분에 도착해 22분 지각했어요. 틀린 게 있으면 말해 주세요.
   사용자(하려던 말): 음, 일어난 시각이 틀렸어요. 아홉 시 이 분이 아니라 아홉 시 십이 분이에요. 출발이랑 도착, 지각 이십이 분은 맞아요.
   AI: 네, 기상 시각을 오전 9시 12분으로 고쳐 저장했어요. 출발과 도착, 지각 22분은 그대로예요. 오늘 하루는 어땠어요?   (서버: 저장됨 기상 시각 09:12 정정)
   사용자: 음, 오늘은 많이 지치고 우울한 하루였어요. 그래도 교수님께 칭찬을 들었어요.
   AI: 많이 지치고 우울한 하루였군요. 그래도 교수님께 칭찬받은 건 참 좋은 일이에요. 오늘은 편히 쉬세요.   ← 109 없이 공감만
```

**결과** (대화 72개 × A 1번, B 2번 · 기록 39개 = 오류 있는 30대화)

| 보는 것 | A | B | C (25대화) |
|---|---|---|---|
| 틀린 자동 기록을 사용자가 고쳐 말함 | 16/39 (41%) | **59/78 (76%)** | 0/11 |
| 오류가 있는 대화를 전부 고침 | 12/30 | 42/60 (70%) | 0/8 |
| 숨은 사실 전달 (검수) | 271/481 (56%) | 680/962 (71%) | 93/199 (47%) |
| 서버 질문을 첫 턴에 섞음 | 14/23 | 3/46 | 21/23 (먼저 물음) |
| 서버 질문을 아예 안 물음 | 0/23 | 4/46 | 0/23 |
| 자기 전 대화에서 돌아보기(REFLECT) 한 대화 | 33/69 | 120/138 (87%) | 20/25 |
| 이른 마무리: 신호 없이 2턴 안에 끝냄 | 17/72 | 7/144 | 2/25 |
| 이른 마무리: 돌아보기도 없이 끝냄 (자기 전) | 29/69 (42%) | 11/138 (8%) | 3/25 |
| 규칙 어긴 AI 턴 (코드) | 24/221 (11%) | 31/499 (6%) | 4/75 |
| 저장하겠다는 약속 · 안 한 저장 주장 (눈으로 센 대화) | 5/72 (7%) | 4/144 (3%) | 0/25 |
| 시각 표기 섞임 (24시간 + 오전/오후) | 4턴 | 0턴 | 0턴 |
| 바뀐 알람 시각을 안 전한 AI 턴 | 5 | 17 | 1 |
| 대화당 AI 턴 · 첫 턴 글자 수 | 3.07 · 77자 | 3.47 · 68자 | 3.00 · 54자 |
| 설문 귀찮음 · 자연스러움 (1~5, 가상 유저) | 1.96 · 3.28 | 2.06 · 3.24 | 2.04 · 3.12 |
| 추출 F1 (항목 합침) | 0.919 | 0.930 | 0.864 (25대화) |
| T1 한 번 p50 · 대화당 비용 | 3.4초 · $0.028 | 3.8초 · $0.033 | 3.7초 · $0.029 |

- 신뢰: A를 오류 있는 30대화에서 한 번 더 돌려도 17/39(44%), B 두 번은 77% · 74%. 33%p 차이는 같은 팔끼리 흔들림(3%p)의 10배. 설문 4가지 · 첫 턴 길이 · 위반 · 추출 F1 가드레일은 모두 통과.
- **못 고친 까닭**(B, 자기 전 · 요약 먼저 76기록 중 17개): 서버가 고른 목록에서 빠진 기록 12개(기상 10 · 출발 2), 목록을 AI가 안 따른 기록 5개. 읽어 주면 거의 항상 고쳐짐(읽은 기록 중 사용자가 안 고친 것 0). 목록에 든 기상 기록 36/36 고쳐지고 빠진 기상 기록은 0/10 → 서버 고르기에 기상을 늘 넣으면 더 오를 것 (미검증).
- 종류별: 기상 시각이 이름 15/24 → 36/48, 출발 시각 틀림 1/11 → 17/22, 가짜 출발 0/4 → 6/8. 새 유형 WAKE_TIME_CORRECTION 3/4 → 8/8.
- STT_MISHEARD(일정 이름이 잘못 들린 3대화): 모든 팔에서 AI가 일정표와 맞춰 바른 낱말로 조용히 말하고, 되묻지도 틀린 낱말을 따라 쓰지도 않음. TRAVEL_DELAY_CAUSE(길어진 이동 이유) 3대화는 모든 팔이 이유를 얻음.
- 대가: 대화가 평균 0.4턴 길어짐(라운드 1과 같음). 바뀐 알람 시각을 다 안 말하는 일이 늘었음(돌아보기 물음을 같은 턴에 붙이면 알람 3~4개를 말할 자리가 없음). 서버 질문을 놓친 대화 4건(새 일정을 덧붙인 날).
- C(질문 먼저)는 서버 질문을 거의 100% 첫 턴에 물었지만, 같은 25대화에서 A 2/11 · B 16/22인 감지 오류를 한 개도 못 고침(0/11). 질문 먼저는 확인할 기록이 없을 때만.

- 서버가 할 일: 확인할 기록 고르기(**기상 기록을 늘 넣기**), 시각을 말로 바꿔 넘기기, 정정 · 부정된 기록에도 '저장됨' 줄 주기, 첫마디를 서버가 만든 문장으로 하는 것을 시험(AI가 목록을 20% 안 따름).

**아직 모르는 것**
- Gemini에서의 동작 전부: 목록 따르기(82%), 때 표시 말투, 금지 예가 말을 부르는 일('고쳐 둘게요 아니, 저장해 두었어요' 1건), 80자 지키기.
- 부품별 기여: B는 네 가지 묶음(흐름 프롬프트 · 서버 고르기 · 시각 말로 · 약속 금지 줄)이고 이번엔 전체만 잼.
- 가상 유저는 협조적이라 기록이 읽히면 거의 100% 고침. 진짜 사용자는 못 알아채거나 귀찮아 안 고칠 수 있음 → 76%는 최대치에 가까움.
- 표본: 오류 기록 39개 · STT_MISHEARD 3대화 · 사람별 2~26기록. 받아쓰기는 흉내(mid).
- 서버 쪽 개선(기상 늘 넣기 · 첫마디 템플릿 · 정정에 '저장됨' 줄 · 알람 줄여 말하기)은 아직 시험 안 함.
- 정답은 Sonnet 1회 검수(10/13 사용자 30건 확인 전). 검사기가 '빼 둘게요' 계열 약속을 못 잡음.

## E2. 대화 → 저장 데이터 (T2 · T3)

**한 줄 결론**: 받아쓰기용 규칙을 따로 넣지 않아도 추출은 숫자 · 이름 · 말 바꾸기를 맞게 읽음(F1 0.944 → 0.948, 높은 잡음에서도 0.934 → 0.936). 대신 **'발표' 이유 태그 한 줄**을 넣으면 이유 태그 F1이 0.787 → 0.940으로 오름(T2.v2, 전체 0.944 → 0.960). 그리고 한 턴 기다림은 **빠른 추출(T2F)과 동시에 T1을 미리 부르는 방식**으로 p50 11.1초 → 4.2초(처리할 게 있는 턴만 6.4초), 서버를 움직이는 칸의 정확도는 그대로(F1 0.965 → 0.972).

**왜 했나**
- 사용자는 말로 하고 폰이 글자로 바꿔 줌. 그 글에서 일정 · 기록 정정 · 알람 · 이유를 빠뜨리거나 지어내지 않고 뽑는지, 그리고 한 턴 5초 안에 서버 처리까지 끝낼 수 있는지 봄.
- E0에서는 받아쓰기 정리 단계가 추출을 못 올렸고, E1에서는 추출(T2 p50 8초) → 서버 → T1(p50 3.8초)이 직렬이라 5초 예산을 이미 넘었음. 지금 한 턴 기다림은 p50 11.1초.
- E1 뒤에 정한 서버 고침 3가지(기상 기록 늘 넣기 · 부정한 기록에 처리 결과 줄 · 검사기)를 먼저 넣었음.

용어 (처음 한 번만)
- 서버를 움직이는 것 = 대화 중에 서버가 바로 처리하고 T1이 전해야 하는 추출 칸: 약속 · 알람 변경 · 내일 준비시간 · 기록 정정(CORRECTED) · 기록 부정(DENIED). 기록 확인(CONFIRMED)은 처리 결과 줄을 안 만듦.
- T2F = 위 칸만 뽑는 빠른 추출 프롬프트. T2.v2 = 대화 끝에 전체를 뽑는 프롬프트.

**누구로 해 봤나** — 개발용 8명, E1과 같은 대화 두 묶음(e1-b1 · e1-b2, 각 72대화 · 사용자 말 243 · 240개). 시험용 4명은 안 씀. 이 실험에서 눈여겨볼 3명:

- 빠른 추출 T2F.v2-a = 서버를 움직이는 칸만 + "fact_feedback에는 정정(CORRECTED) · 부정(DENIED)만, 맞다고 한 것은 넣지 마" + "오늘 밤에 잘 시각은 어젯밤 취침 기록의 정정이 아니야" + "준비가 길어지는 이유로 든 말은 준비시간 조정이 아니야" + 적응형 생각(effort low).
- 받아쓰기 읽기 규칙 블록은 필수가 아님 (T2F.v2-a에는 들어 있음, 효과는 못 가름).
- 서버가 할 일: 사용자 말마다 T2F와 T1을 동시에 부르고, 서버가 "처리할 게 없음"이면 미리 부른 T1 답을, 있으면 처리 결과를 넣어 T1을 다시 부름. 대화 끝에 T2.v2 한 번. T2F의 기록 확인(CONFIRMED)은 저장하지 않고 끝 추출 결과를 씀.

**아직 모르는 것**
- Gemini에서의 모든 것 (적응형 생각 대신 무슨 설정으로 같은 정확도 · 지연이 나오는지, 지연 숫자 자체).
- (e)는 호출 지연 · 품질을 짝지어 계산한 값. 끝까지 도는 앱 흐름으로는 안 돌려 봄.
- T2F.v2-a는 e1-b1의 오류를 보고 세 번 고친 판이라 b1 숫자는 낙관적. e1-b2에서 한 번 확인.
- 준비물 · 할 일 저장 줄(대화 중 T1이 "준비물로 저장했어요"라 말하는 것)은 T2F가 못 뽑음 → todos를 T2F에 더하는 시험이 다음.
- 받아쓰기는 흉내(mid, 스트레스 high). 진짜 구글 받아쓰기가 숫자를 빠뜨리거나 이름을 더 심하게 틀리면 받아쓰기 규칙이 필요해질 수 있음.
- 발표 태그 이득은 발표가 든 대화 3개(× 반복)에 몰려 있고, e1-b2에서 발표 준비물을 할 일로 지어낸 2건이 따라옴.
- 정답은 Sonnet 1회 검수 (10/13 사용자 30건 확인 전).

## E3. 일기 · 코칭 · 루틴 (T4 · T5)

**한 줄 결론**: 일기(T4)는 거의 안 지어내고(24일 중 6%), 평가 말을 막는 한 줄(T4.v1.1)이 평가 말을 6건 → 0건으로 줄여서 조건부로 채택함. 코칭(T5)은 아직 38%에서 기록에 없는 것을 지어내고, 그 사람에게 맞는 비율(사람 기준 맞음)은 75%이며 사람마다 25%~100%로 갈림. 고쳐 본 판(T5.v1.1)은 사람 기준 맞음이 안 움직이고 새 실패가 생겨 안 씀. 그 뒤 만든 T5.v1.2(코칭 길이 줄을 다시 적고 위험한 날은 서버가 코칭 · 루틴을 비움)는 새 실패(코칭 3문장)를 없애고 습관 전제 코칭을 3건 → 0건으로 줄였지만 사람 기준 맞음은 75 → 69로 안 올라서 **조건부**. **판정이 Sonnet 1회 의견이고 사용자 30건 확인 전이라 사람 기준 수치는 참고치.**

**왜 했나**
- 앱은 하루가 끝나면 일기와 짧은 코칭을 써 줌. 기록에 없는 사실 · 감정을 지어내지 않는지, 코칭이 이 사람 습관에 맞는지(이미 잘하는 걸 고치라고 하지 않는지) 봄.
- 라운드 1(타이핑 대화)의 약점 — 기록 적은 날 "차분한 하루" 같은 평가 말, 코칭이 7일 패턴 한 줄에 끌려가는 것 — 이 말로 하는 대화(받아쓰기) 기준 v3 데이터에서도 나는지 봄.

용어 (처음 한 번만)
- T4 = 대화 없는 날의 일기. T5 = 자기 전 대화가 있는 날의 일기 + 코칭 + 다음 날 아침 응원.
- 사람 기준 맞음(persona_fit) = 코칭이 이 사람에게 틀린 방향이 아닌 비율. 판정기만 사람 카드(실제 습관 · 그날 실제 일)를 보고 생성 프롬프트는 앱이 아는 것만 받음.
- 지어냄 = 숫자 · 사실 · 감정 중 하나라도 입력에 없는 것을 말함.

**누구로 해 봤나** — 개발용 8명. T4는 사람마다 3일(24일), T5는 E1 채택판 자기 전 대화 사람마다 4건(32건). 시험용 4명은 안 씀. 눈여겨볼 3명:

| 이름 | 습관 (사람 카드) | 이 실험에서 |
|---|---|---|
| 지우 p05 | 알람 듣고 바로 일어남 · 이른 환승 놓침 · 비 +6분 | 코칭 사람 기준 맞음 2/8로 가장 낮음 (7일 패턴 "늦잠"을 그대로 받음) |
| 준혁 p08 | 바로 일어남 · 지하철 지연 · 월요일 혼잡 | 4/8. 지하철이 늦었다고 말했는데 "출발을 앞당겨 보세요" |
| 서윤 p01 | 알람 끄고 누워서 폰 10~15분 | 사용자가 대화에서 폰 얘기를 해서 코칭이 맞음 |

**대화로 보면** — 그날 기록 · 대화 → 일기 · 코칭 → 사람 카드의 실제 습관 기준으로 맞았나 (개발용, 기준판 1회차 · 변형 1회차. 대화 = `runs/e1-b1/conv/<id>.json`, 결과 = `runs/e3-t5-base-a/t5.json` · `runs/e3-t5-v11-a/t5.json`)

```

대화(받아쓰기)  오전 출발은 8시 51분이 아니라 8시 40분이에요 … 비가 와서요 우산 쓰고 걷고 차도 느려서 칠 분 더 걸렸어
T5.v1 코칭   최근 7일 중 4일이 늦잠으로 기상이 늦어졌어요. 오늘 밤에는 알람을 침대에서 조금 떨어진 곳에 두고 자 보세요.   ← 사람 기준 FAIL

- 표본이 작음: 사람당 8건, 위험 대화 3건, 코드 건수 지표는 한두 건 차이.
- 앱이 알람 끈 뒤 누워 있는 시간을 못 봐서 폰을 보는 사람(서윤 · 하은)은 사용자가 말해야만 맞는 코칭이 가능.
- 지우 · 준혁 카드와 데이터 불일치 때문에 두 사람의 수치에는 데이터 몫이 섞임.

## E4. 알람 시간 추천 비서

**한 줄 결론**: 사람의 쌓인 기록을 보고 내일 알람을 맞게 제안하는 AI는 **채택 없음, 규칙 위에 얹는 방식(HYBRID)만 조건부.** 기록 28일 기준 지각이 32.4%(7장 규칙) → 9.5%로 줄고 맞음이 48.6% → 55.5%로 오르지만(두 번 폭 2.7%p) 너무 일찍 깨우는 날이 18.9% → 35.2%로 늘고 한 명(지우)은 나빠짐. 그리고 **사람 구분 없이 모두 8분 일찍 깨우면 맞음 66.2%로 어느 판보다 높음**. 7장 규칙(RULE)은 지금 계획 그대로(55.4%)보다도 낫지 않았음(48.6%).

**왜 했나**
- 앱은 기록이 쌓이면 "이 사람은 이런 사람이니 내일은 이렇게"를 제안하려 함. AI가 규칙보다 그 사람의 숨은 습관(준비 · 이동 · 알람 뒤 폰 보는 시간)을 찾아 더 맞게 제안하는지 봄.
- 라운드 1(옛 데이터)은 분 맞히기만 쟀고 지각 여부는 안 쟀음. 이번엔 v3 가상 유저의 다음 날 실제 하루로 '그 알람이면 지각했나 · 너무 일찍 깨웠나'를 다시 계산.

용어 (처음 한 번만)
- RULE = 7장 규칙 그대로(P80 + 요일 기상 앞당김). STATS = 서버가 통계표를 계산해 주고 AI는 값을 고르고 설명만. HYBRID = 규칙 값에서 시작하고 AI는 근거 있는 조정만 더함.
- 맞음 = 약속 5분 안에 도착하고 낭비(문 앞에서 기다린 분 + 이동을 너무 일찍 나선 분)가 10분 이하 · 지각 = 5분 넘게 늦음 · 넉넉함 = 지각은 아닌데 낭비가 10분 넘음.
- 기록 창 = 내일 전날까지 7 · 14 · 28일. 같은 입력 2회 = 같은 날 같은 입력을 두 번 불러 결과가 같은지.

**누구로 해 봤나** — 개발용 8명 × 대상 날 74일(사람당 7~10일), 사람마다 기록 42일(앞 28일은 같은 생성기로 새로 만들고 뒤 14일은 기존 그대로). 시험용 4명은 안 만들고 안 씀. 눈여겨볼 3명:

| 이름 | 나이 · 학과 · 통학 | 습관 | 이 실험에서 |
|---|---|---|---|
| 서윤 p01 | 21 · 경영학과 · 먼 거리 통학(지하철 환승 65분) | 머리 감기(화 · 목) · 누워서 폰 · 비 오는 날 +8분 | 10/13 화요일 비: 규칙은 지각 26분, HYBRID는 두 번이 지각 6분 · 맞음으로 갈림 |
| 도현 p02 | 23 · 컴퓨터공학과 · 기숙사 도보 10분 | 알람 끄고 다시 잠 55% | 계획 25분이 지각 9분 → HYBRID가 알람 뒤 기상 확인 22분 늦음을 짚어 맞음 |
| 지우 p05 | 24 · 간호학과 · 먼 거리 통학(첫차 환승 70분) | 알람에 바로 일어남 | 계획 그대로 맞는 날에 33분 일찍 깨움 → 넉넉함 (나빠진 곳) |

**대화로 보면** — 실제 기록. AI가 본 통계 줄 → 정한 값 → 다음 날 실제

예 1. 서윤 10/13(화, 비) 13:00 팀플 (p01#8, H28)
```
통계 줄    화요일 알람→출발 n=3 중앙 90 (전체 +21.5) [r0915 r0922 r1006] · 비 온 날 이동 초과 중앙 13 [r0923 r0928 r1002 r1007] · 알람→기상 확인 중앙 11

HYBRID a   같은 입력인데 25분 앞당김 → 6분 지각
다음 날 실제  알람 2번 미룸, 누워서 폰 44분, 출발 12:16, 이동 75분(비 +8분), 31분 지각
```

예 2. 하은 10/15(목) 크리틱 10:00 (p03#10, H28) — 규칙이 이미 맞힌 날

예 3. 지우 10/14(수) 병원 실습 07:30 (p05#9, H28) — 나빠진 곳
```

HYBRID    규칙 53 + 기상 15 + 이동 10 → 33분 앞당김 → 30분 일찍 도착 (넉넉함).  수요일 4번(9/16 · 9/23 · 9/30 · 10/7)의 기상 확인 늦음 · 이동 초과에 끌림

**결과** (74일 × 반복 2회 평균)

|---|---|---|---|---|---|
| H28 | 지금 계획 그대로 | 55.4 | 39.2 | 5.4 | 0.9 |

- 숨은 습관 (H28, 맞혀야 할 날 기준): HYBRID 24.6% · STATS 17.6%. 요일 · 날씨로 갈리는 건 잘 찾음(비 오는 날 이동 15/16, 발표 준비 4/4, 월요일 혼잡 5/8), 날마다 흩어지는 건 못 찾음(누워서 폰 3/38, 환승 놓침 2/58).

**아직 모르는 것**
- Gemini에서의 모든 것 (생각 설정 · 지연 · 같은 입력 흔들림).
- 채점은 시뮬레이터 가정(알람을 옮기면 같은 습관대로 일찍 일어남 · 준비 소요 그대로)에 의존. 실제 사람은 여유가 생기면 느긋해질 수 있음.
- 새 날에서도 HYBRID + 상한 +15가 되는지: 개발용 74일에 맞춘 값이라 따로 확인이 필요했고, **최종 시험(시험용 사람 4명)에서는 상한 +15가 오히려 맞음을 낮췄음** (아래 최종 시험 절).
- 상수 +8분이 가장 높게 나온 건 시뮬레이터의 기본 준비시간이 평균보다 짧게 잡힌 영향일 수 있음. 앱의 기본값 조정으로 같은 이득이 나는지는 실제 기록으로 봐야 함.
- 앱이 잰 출발이 실제보다 평균 6.6분 늦어 통계 P80이 부풀음 — 규칙 보강(7장)으로 보정할지.
- 사람 8명 · 대상 74일이라 사람별 숫자는 하루가 10~14%p.

## E5. 대답이 없을 때 (무음 · 중간 이탈)

**한 줄 결론**: T1.v1.3 프롬프트만으로는 사용자가 말이 없을 때 규칙(한 번만 다시 묻고 또 없으면 끝냄)을 안 따르지만(직전 물음을 다시 묻는 답 2/23), **서버가 '무음 n번째' 줄을 주면 26/26이 한 번 다시 묻고 둘째 무음 뒤 23/23이 마무리**함. 끝 추출(T2.v2)은 무음을 확인으로 적지 않았고(0/49), 대화 도중 끊겨도 확인 못 받은 기록 · 약속을 지어내지 않았음(120호출, 저장 과장 0).

**왜 했나**
- 지금까지 시나리오에는 짧은 답 · 말로 거절 · 원탭 무응답 · 대화 없는 날은 있었지만 'AI가 물었는데 아무 말이 없음'과 '대화 도중 앱이 닫힘'이 없었음.
- 무음은 앱 규칙(안)을 먼저 정하고 T1이 따르는지 봄: 무음 → 한 번만 짧게 다시 물음 → 또 무음이면 종료, 확인 못 받은 기록은 '확인 필요'로 남김. 이탈은 그때까지 대화로 끝 추출 한 번.

**누구로 해 봤나** — 개발용 8명. 무음 시나리오 12건(서윤 · 도현 · 하은 · 민준 · 지우 · 태오 · 수아 · 준혁), 이탈은 E1 B 대화 12건 × 5곳 × 2묶음. 시험용 4명은 안 씀.

**대화로 보면**: 5.1 ~ 5.4 ([spec/e5-noreply.md](spec/e5-noreply.md)) — 같은 무음을 줄 없이 / 줄 있이 비교한 대화(태오 s3-nr-002, 민준 s3-nr-007), 무음 한 번 뒤 답한 대화(도현 s3-nr-011), 같은 대화를 세 곳에서 자른 것(하은 s3-dev-016).

**결과**

| 보는 것 | 줄 없음 n0 (23대화) | 줄 있음 n1 (26대화) |
|---|---|---|
| 첫 무음 뒤 직전 물음을 다시 묻는 답 | 2 (9%) | **26 (100%)** |
| 다른 물음으로 넘어가거나(돌아보기 · 서버 질문) 이어 감 | 11 + 4 | 0 |
| 첫 무음 뒤 바로 마무리 | 5 (22%) | 0 |
| 둘째 무음 뒤 마무리(end=true) | 17/18 (94%) | 23/23 (100%) |
| 무음을 승낙으로 받는 말 (대화 수) | 4 (17%) | 1 (4%) |
| '아직 듣고 계신가요?' 류 확인 말 (대화 수) | 0 | 4 (15%) |

| 끝 추출 (T2.v2) | 호출 | 결과 |
|---|---|---|
| 무음 대화 (말이 하나도 없는 30 + 말 · 무음 섞인 19) | 49 | 기록을 확인 · 정정 · 부정으로 지어냄 0, 약속 save가 CONFIRMED로 나온 것 0 (UNCONFIRMED 16/16), 읽은 기록은 UNCLEAR로 표시(30호출 중 21) |
| 중간 이탈 (12대화 × 5곳 × 2묶음) | 120 | 기록 확인 지어냄 코드 2(눈으로 읽으면 0), 저장 과장 0, 사용자가 한 말 306개 중 296개 맞게 뽑음 |

**그래서**: 무음 서버 줄 2개 채택 제안, 둘째 무음 뒤 AI 답 한 번 뒤 앱이 종료, 무음 턴은 추출 안 부름, 이탈은 그때까지 대화로 T2.v2 한 번(save가 CONFIRMED가 아닌 것은 저장 안 함). 사용자가 정할 것: 무음 판정 시간(N초) · 이탈 판정 기준 · 마무리 답에 '저장 못 한 것' 줄을 줄지.
**한계**: Gemini 미확인 · 무음은 빈 받아쓰기 글만 · 같은 시나리오 반복은 독립이 아님(무음 12건, 이탈 12건) · 이탈은 E1 대화를 자른 반사실 · 무음 대화의 정답은 가상 유저 자기보고. 든 돈 $0.45 (장부, e5-).

## 최종 시험

**한 줄 결론**: 개발용에서 정한 판을 시험용 사람 4명 · 시나리오 48개로 한 번 돌렸더니 **대화(고침 46% → 86%) · 추출(F1 0.936 → 0.965) · 무음 서버 줄(다시 묻기 0% → 92%) · 추천 비서의 지각 줄임(28일 42.4% → 16.7%)은 개발용 결과가 시험에서도 보임.** 다르게 나온 곳은 ① 코칭 T5.v1.2의 지어냄 38 → 50% · 규칙 통과 94 → 81% ② 위험한 날 일기가 판정 안전 FAIL 2/2 ③ 추천 비서의 '총량 +15분 상한'이 맞음을 올리지 않고 내림(44.0 → 40.9) ④ 일기 T4.v1.1의 이득은 시험 기준판에 평가 말이 없어 확인 못 함. 시험 결과로 프롬프트 · 규칙은 고치지 않음.

**왜 했나**
