# 실험정리 — 앱 지점별 AI 프롬프트 실험 (v3, 음성 받아쓰기 기준)

> 실험 하나가 끝날 때마다 한 장씩 채움. 모양은 [보고서_설계.md](보고서_설계.md) 2절, 계획은 [실험계획_v3.md](실험계획_v3.md).
> 모든 실험은 Claude Haiku 5.5로 했고 운영 모델 Gemini에서는 확인 안 됨.

용어 (처음 한 번만)
- 받아쓰기(STT) = 폰이 마이크로 들은 말을 글자로 바꿔 주는 기능. 앱은 안드로이드 기본(구글) 음성 인식을 가정함. 실제 엔진이 아니라 규칙으로 흉내 낸 잡음을 씀.
- T0 받아쓰기 정리 · T1 대화 답 · T2 저장할 것 뽑기. 번호는 앱 지점 이름표.
- F1 = 말한 것 중 맞게 뽑은 비율과, 뽑은 것 중 맞는 비율을 합친 점수 (1.0이 만점).
- 정답(gold) = 검수자가 '사용자가 실제로 한 말'(하려는 말)을 다시 읽고 만든 표.
- 감지 오류 기록 = 앱이 자동으로 잰 기록(기상 · 출발 · 도착)인데 실제와 다른 것. 사용자가 "그건 아니에요"라고 고쳐 말해야 앱이 배움.
- 서버 질문 = 서버가 정해 주는 물음(예: 지각 이유). 돌아보기(REFLECT) = "오늘 하루 어땠어요?"처럼 하루를 돌아보는 물음. 이른 마무리 = 사용자가 끝내자는 신호를 안 줬는데 AI가 먼저 끝냄.

## E0. 받아쓰기 정리 (T0)

**한 줄 결론**: 받아쓰기를 정리하는 단계를 따로 두지 않아도 됨 — 정리 없이 넣은 추출 점수(F1 0.925)가 하려는 말을 그대로 넣은 점수(0.927)와 사실상 같아서 정리가 올릴 여지가 없고, 정리하면 뜻이 1.5~2%(추정) 바뀌고 한 턴이 1.2초 느려짐.

**왜 했나**
- 사용자는 말로 하고 폰이 글자로 바꿔 주는데, 그 글에는 숫자가 '일곱 시 반'과 '7시 30분'으로 섞이고, 군말 · 말 바꾸기 · 비슷한 소리 오류가 있음.
- "이 글을 LLM이 한 번 정리해 주면 뒤 단계(저장할 것 뽑기 · 답)가 나아지나?"를 보려고 했음. 정리한 글은 사용자에게 안 보이고, 잘 안 들린 곳은 표시해서 T1이 자연스럽게 되묻게 하려는 계획이었음.

**누구로 해 봤나** — 개발용 8명, 한 명당 9대화 (유형 24가지 × 3 = 72대화, 사용자 말 202개). 시험용 4명은 안 씀.

|---|---|---|---|---|---|
| 서윤 p01 | 21 · 경영학 | 지하철 환승 65분 | 차분한 존댓말, 틀린 기록은 정확히 고침 | 가끔 | 누워서 폰 10~15분 |
| 도현 p02 | 23 · 컴공 | 기숙사 10분 | 짧고 무심한 반말, 말끝 흐림 | 가끔 | 다시 잠 |

| 민준 p04 | 22 · 기계공학 | 자취 20분 | 존댓말 반말 섞음, 숫자를 말 그대로 읽음 | 가끔 | 바로 일어남 |

사람 카드 전체 = `spec/v3-setup.md` 2절 · data/v3/personas.json.

**대화로 보면** — 같은 사용자 말 하나에 정리 방식별로 어떻게 달라졌나 (실제 기록, 정리 판 이름: v0 = 이름 목록 없이, ctx = 앱의 일정 · 장소 · 사람 이름 목록을 같이 줌, 고친 판 ctx01)

예 1. 이름이 틀리게 적힌 경우 (민준 p04, 대화 s3-dev-071, 사용자 말 1)

```
AI        오늘은 14시 1분에 일어나 15시 조별 발표에 6분 늦게 도착했고, 18시엔 로봇 동아리에 갔어요. 틀린 기록이 있으면 말해 주세요.
하려던 말   음 그 기상 시각은 틀렸어요. 실제로는 한 시 오십일 분에 일어났어요. 나머지는 맞아요. 아 그리고 내일 열역학이 아홉 시에서 열한 시로 바뀌었어요.
받아쓰기   음 기상 시각은 틀렸어요 실제로는 1시 51분에 일어났어요 나머지는 맞아요 아 그리고 내일 열력학이 9시에서 열한 시로 바뀌었어요
정리 v0    … 내일 열력학이 9시에서 11시로 바뀌었어요.   ← 이름은 그대로, 숫자만 통일. [표시: 열력학 — '열역학'의 오인식일 수 있음]
정리 ctx   … 그리고 내일 열역학이 9시에서 11시로 바뀌었어요.   ← 목록 이름으로 되살림. [표시: '1시 51분' 오전/오후 — 헛짚음]
정리 ctx01 … 그리고 내일 열역학이 9시에서 11시로 바뀌었어요.   ← 표시 없이 되살림
T2 추출    (받아쓰기 그대로 · v0 · ctx · 합친 판 · 하려던 말 모두 같음)
           약속 a3 열역학 10/14 11:00 (시각 변경) · 기록 f2 정정 13:51 · 나머지 기록 확인
```
- 정리는 이름을 되살렸지만(ctx) 추출 결과는 안 달라짐. T2가 일정표에서 '열역학'(a3)을 찾아 짝지음.
- T1의 답(받아쓰기 그대로 받은 경우): "기상 시각을 13시 51분으로 고쳐 저장했어요. 내일 열역학을 11시로 옮기는 것도 저장할까요?" — 틀린 이름을 말하지 않고 조용히 맞춰 말함.

예 2. 말 바꾸기 + 이름 소리 틀림 (준혁 p08, s3-dev-021, 사용자 말 1)

```
하려던 말   … 그런데 내일 계량경제학이 아홉 시 아 아니 열 시로 바뀌었어요.
받아쓰기   … 그런데 내일 계략경제학이 아홉 시 아 아니 10시로 바뀌었어요.
정리 v0    … 그런데 내일 계략경제학이 10시로 바뀌었어요.   ← 말 바꾸기 정리됨, 이름은 그대로 [표시: 계략경제학]
정리 ctx   … 그런데 내일 계량경제학이 10시로 바뀌었어요.   ← 둘 다 됨 [표시: 목록 이름으로 고쳤지만 확실치 않음]
T2 추출    (모든 입력 같음) 약속 a1 계량경제학 10/12 10:00
```
- 받아쓰기 그대로여도 T2는 '아홉 시 아 아니 10시' 중 마지막 값을 씀.

예 3. 정리가 숫자를 틀리게 바꾼 경우 (도현 p02, s3-dev-004, 사용자 말 1)

```
하려던 말   어 그냥 알람 끄고 다시 잤어. 한 십일 분쯤 더.
받아쓰기   어 그냥 알람 끄고 다시 잤어 한 십일 분쯤 더        ← 받아쓰기는 맞음
정리 v0    그냥 알람 끄고 다시 잤어. 한 10분쯤 더.        ← 11분이 10분으로 (틀림)
정리 ctx   그냥 알람 끄고 다시 잤어. 한 10분쯤 더.        ← 같은 실수
정리 ctx01 그냥 알람 끄고 다시 잤어. 11분쯤 더.            ← 고쳐짐 ('한'은 빠짐)
T2 추출    (모두 같음) 이유 OVERSLEPT (늦잠)
```
- 이런 숫자 실수가 143개 중 1~2개 (v0 · ctx 2개, 고친 판 1개 — 다른 말). T2가 분을 안 쓰는 대화라 점수는 안 변했지만, 분을 저장하는 대화였다면 틀린 값이 저장됨.
- '오십일 분 → 50분'(s3-dev-065)도 같은 실수.

예 4. 표시를 받은 T1이 되묻는 경우 (지우 p05, s3-dev-011, 사용자 말 1)

```
하려던 말   네, 기상 시각은 맞아요. 아, 준비물은 학생증이랑 컴퓨터용 사인펜 챙길 거예요.
받아쓰기   네 기상 시각은 맞아요 아 준비물은 헉생증이랑 컴퓨터용 사인펜 챙길 거예요
정리 ctx01 … 준비물은 학생증이랑 컴퓨터용 사인펜 챙길 거예요.   [표시: 헉생증 — '학생증'으로 고쳤으나 확실하지 않음]
서버가 T1에 전하는 처리 결과  되물을 것: 받아쓰기 확인: '헉생증'이(가) 제대로 들렸는지 (…)
T1 (받아쓰기 그대로)  좋아요, 학생증이랑 컴퓨터용 사인펜 챙기는 걸로 저장해 두었어요. …
T1 (표시 받음)       좋아요, 학생증이랑 컴퓨터용 사인펜 챙기는 걸로 저장해 뒀어요. 혹시 '헉생증'이 아니라 '학생증'이 맞는지 확인해 줄래요?
```
- 표시를 받으면 T1이 시킨 대로 물음 1개로 되묻음. 그러나 '학생증'은 뻔해서 사용자는 어색할 수 있음 — 표시의 기준이 너무 후함.
- 정말 모르는 말에서는 필요한 되묻기도 나옴: "장소는 씬촌역이 맞는지 신촌역인지 한 번만 확인할게요" (s3-dev-043).

**결과** (대화 72개 · 사용자 말 202개 · 정리 호출 말마다 1번)

| 보는 것 | 받아쓰기 그대로 | 정리 v0 | 정리 ctx | 고친 판 ctx01 |
|---|---|---|---|---|
| 숫자 143개 중 맞게 살린 | 143 | 141 | 141 | 142 |
| 앱이 아는 이름이 틀린 7번 중 되살린 | 0 | 1 | **6** | 5 |
| 새 일정 이름이 틀린 11번 중 되살린 | 0 | 4 | 6 | 6 |
| 말 바꾸기 3번 중 앞 값을 지운 | 0 | 3 | 3 | 2 |
| 뜻이 바뀐 말 (표본 30개 중) | — | 4 | 3 | 0 |
| 하려는 말에 없는 새 낱말이 든 말 (202 중) | 0 | 5 | 8 | 4 |
| 추출 F1 (대화 72 × 2번) | **0.925** | 0.917 | 0.925 | 0.919 |
| 한 턴에 더해지는 시간 p50 / p95 | 0 | 1.2초 / 2.0초 | 1.2초 / 1.9초 | 1.1초 / 1.9초 |

- 하려는 말을 그대로 넣은 추출 F1이 0.927 → 정리가 올릴 수 있는 최대치가 0.002. 같은 입력을 두 번 돌려도 0.926 → 0.923으로 흔들려서(대화 8/72가 다르게 나옴) 이 차이는 구분 안 됨.
- 잡음을 high로 올려도(틀린 새 이름 21곳) 받아쓰기 그대로의 F1은 0.923. 정리는 틀린 새 이름 21곳 중 15~17곳을 고치지만 점수는 0.914~0.924로 같음.
- 정리가 숫자를 가끔 틀리고(143개 중 1~2개), 잘린 말을 짐작으로 채우고('안녕히' → '안녕히 계세요'), 고친 판은 짧은 답에서 지시문을 따라 적기도 함 (202말 중 1~2건, 서버가 길이 · 지시 낱말로 막아야 함).
- 표시: 정리가 짚은 곳의 3분의 2는 헛짚음(v0 34개 중 23). 고친 판은 26개 중 13이 실제 잡음. 그래도 받아쓰기가 틀린 34곳 중 13곳만 짚음.
- 표시를 T1에 되물을 것으로 넘기면, 실제로 틀린 31곳 중 되묻는 곳이 8 → 17. 대신 잡음이 없는데 표시 때문에 물은 곳이 8곳 중 3.
- 돈은 말 한 번에 $0.00007 (Haiku, 생각 끔). 시간이 비용.

**그래서 프롬프트에 넣을 말**
- 이 지점(①)은 **호출하지 않음**. T2 · T1 프롬프트에 받아쓰기 안내 문단도 넣지 않음 (넣은 판도 0.918로 같았고 문단이 쓰인 흔적이 없음).
- 나중에 정리 호출이 필요해지면 [프롬프트카드/01-받아쓰기정리.md](프롬프트카드/01-받아쓰기정리.md)의 T0.v0.1-ctx를 쓰고, 핵심은 3문장:
  - "단 뜻과 낱말은 바꾸지 마: 사용자가 하지 않은 말은 절대 더하지 마."
  - "글이 끝에서 잘린 듯해도 짐작으로 완성하지 마. 잘린 그대로 두고 uncertain에 적어."
  - "한자어 수는 글자 그대로 더해서 읽어: 십일 = 10 + 1 = 11."
- 서버가 막을 것: 정리본이 받아쓰기보다 1.5배+10자 넘게 길거나 절반 미만이면, 또는 '위 글을 정리해' · '처리:' 같은 낱말이 있으면 받아쓰기 글로 되돌림. 위험한 말 감지는 정리 전 받아쓰기 글에 한 번 더.

**아직 모르는 것**
- 진짜 구글 받아쓰기의 틀리는 모양 (흉내 두 수준만 봄). 이보다 훨씬 나쁘면 결론이 바뀔 수 있음 → 앱 개발 중 실제 받아쓰기 30건쯤 모아 다시 보는 게 가장 확실함.
- Gemini에서의 동작 전부 (생각 끄기 · 숫자 읽기 · 추론이 글에 새는 실패).
- 정리한 글로 대화가 이어졌을 때 T1이 다르게 묻는 흐름 (기준 대화는 받아쓰기 그대로 만든 것). E1에서 '모르는 곳 되묻기' 켠 판과 끈 판을 사람 평가로 비교해야 함.
- 표본이 작은 곳: 말 바꾸기 4말, 새 이름 11곳, 뜻 판정 30말.
- 가상 유저 SIM.v3.1: 한자어 시각('칠 시 육 분')이 10말에 나옴, 수다쟁이 2명 18대화 중 5대화가 스스로 '지어냄'이라 보고.
- 라운드 1 숫자(저장 · 약속 말투 검사)는 옛 검사기로 센 것. 새 검사기로 다시 세면 라운드 1 T1 변형 대화는 걸리는 AI 턴이 10~37% 늘어남 (예: fv1-c1 244턴 중 30 → 41, freeze-v0은 그대로 55).

## E1. 자기 전 · 기상 후 대화 답 (T1)

**한 줄 결론**: AI가 읽어 주는 기록을 서버가 골라 주고(확인할 기록), 시각을 서버가 '오후 6시 30분'처럼 말로 바꿔 넘기고, 첫마디를 기록 확인만으로 줄이면 — 앱이 잘못 잰 기록을 사용자가 고쳐 말한 비율이 39개 중 16개(41%) → 78개 중 59개(76%)가 됨. 대가는 대화 +0.4턴 · 한 번 +0.4초. 서버 질문부터 시작하면(C) 11개 중 0개.

**왜 했나**

자세한 표 · 파일 위치 · 다시 돌리는 법 = [spec/e1.md](spec/e1.md)

## E2. 대화 → 저장 데이터 (T2 · T3)

**한 줄 결론**: 받아쓰기용 규칙을 따로 넣지 않아도 추출은 숫자 · 이름 · 말 바꾸기를 맞게 읽음(F1 0.944 → 0.948, 높은 잡음에서도 0.934 → 0.936). 대신 **'발표' 이유 태그 한 줄**을 넣으면 이유 태그 F1이 0.787 → 0.940으로 오름(T2.v2, 전체 0.944 → 0.960). 그리고 한 턴 기다림은 **빠른 추출(T2F)과 동시에 T1을 미리 부르는 방식**으로 p50 11.1초 → 4.2초(처리할 게 있는 턴만 6.4초), 서버를 움직이는 칸의 정확도는 그대로(F1 0.965 → 0.972).

**왜 했나**
- 사용자는 말로 하고 폰이 글자로 바꿔 줌. 그 글에서 일정 · 기록 정정 · 알람 · 이유를 빠뜨리거나 지어내지 않고 뽑는지, 그리고 한 턴 5초 안에 서버 처리까지 끝낼 수 있는지 봄.
- E0에서는 받아쓰기 정리 단계가 추출을 못 올렸고, E1에서는 추출(T2 p50 8초) → 서버 → T1(p50 3.8초)이 직렬이라 5초 예산을 이미 넘었음. 지금 한 턴 기다림은 p50 11.1초.
- E1 뒤에 정한 서버 고침 3가지(기상 기록 늘 넣기 · 부정한 기록에 처리 결과 줄 · 검사기)를 먼저 넣었음.

용어 (처음 한 번만)
- 서버를 움직이는 것 = 대화 중에 서버가 바로 처리하고 T1이 전해야 하는 추출 칸: 약속 · 알람 변경 · 내일 준비시간 · 기록 정정(CORRECTED) · 기록 부정(DENIED). 기록 확인(CONFIRMED)은 처리 결과 줄을 안 만듦.
- T2F = 위 칸만 뽑는 빠른 추출 프롬프트. T2.v2 = 대화 끝에 전체를 뽑는 프롬프트.

**누구로 해 봤나** — 개발용 8명, E1과 같은 대화 두 묶음(e1-b1 · e1-b2, 각 72대화 · 사용자 말 243 · 240개). 시험용 4명은 안 씀. 이 실험에서 눈여겨볼 3명:

- 빠른 추출 T2F.v2-a = 서버를 움직이는 칸만 + "fact_feedback에는 정정(CORRECTED) · 부정(DENIED)만, 맞다고 한 것은 넣지 마" + "오늘 밤에 잘 시각은 어젯밤 취침 기록의 정정이 아니야" + "준비가 길어지는 이유로 든 말은 준비시간 조정이 아니야" + 적응형 생각(effort low).
- 받아쓰기 읽기 규칙 블록은 필수가 아님 (T2F.v2-a에는 들어 있음, 효과는 못 가름).
- 서버가 할 일: 사용자 말마다 T2F와 T1을 동시에 부르고, 서버가 "처리할 게 없음"이면 미리 부른 T1 답을, 있으면 처리 결과를 넣어 T1을 다시 부름. 대화 끝에 T2.v2 한 번. T2F의 기록 확인(CONFIRMED)은 저장하지 않고 끝 추출 결과를 씀.

**아직 모르는 것**
- Gemini에서의 모든 것 (적응형 생각 대신 무슨 설정으로 같은 정확도 · 지연이 나오는지, 지연 숫자 자체).
- (e)는 호출 지연 · 품질을 짝지어 계산한 값. 끝까지 도는 앱 흐름으로는 안 돌려 봄.
- T2F.v2-a는 e1-b1의 오류를 보고 세 번 고친 판이라 b1 숫자는 낙관적. e1-b2에서 한 번 확인.
- 준비물 · 할 일 저장 줄(대화 중 T1이 "준비물로 저장했어요"라 말하는 것)은 T2F가 못 뽑음 → todos를 T2F에 더하는 시험이 다음.
- 받아쓰기는 흉내(mid, 스트레스 high). 진짜 구글 받아쓰기가 숫자를 빠뜨리거나 이름을 더 심하게 틀리면 받아쓰기 규칙이 필요해질 수 있음.
- 발표 태그 이득은 발표가 든 대화 3개(× 반복)에 몰려 있고, e1-b2에서 발표 준비물을 할 일로 지어낸 2건이 따라옴.
