# 프롬프트 카드 ⑤ 추천 비서 (내일 알람 · 준비 시간 제안)

> 조건 ④(알람 자동 변경 없이 카드로만)는 S01 알람 조정 제안(D53 · D23 · D24 · #49)과 같은 방향. 서버 값(P80 · 총량 상한 +15분)은 D53 '직접 수정 범위'와 #49 시작 때 같이 정함.
> 10/14 E4 결과로 채움. 근거 = [실험정리용 초안](../spec/e4.md) · [spec/e4.md](../spec/e4.md). 서버가 할 일 = [06-서버지침.md 4.3절](06-서버지침.md) (46~53번, 초안 원문은 [spec/e4.md 7절](../spec/e4.md)). 10/15: 최종 시험(시험용 4명) 수치를 '잘 되는 것 · 아직 안 되는 것'에 넣음 — 상한 +15분은 시험에서 근거가 약해짐.
> 모든 동작은 Claude Haiku 5.5에서 본 것이고 **Gemini에서는 확인 안 됨**.

**결정: 채택한 판은 없고, HYBRID(규칙 값 + AI는 근거 있는 조정만, 프롬프트 v1.1)를 조건부로 씀.** 조건 = ① 같은 칸에 근거 검사를 통과한 패턴이 있을 때만 서버가 AI의 늘림을 받음 ② 규칙 값 위에 더하는 총량 상한(진단값 +15분, 새 날에서 확인 필요) ③ 하루 한 번 밤에 정해 저장, 다시 안 부름 ④ 새 날에서 확인하기 전에는 알람 자동 변경 없이 설명 · 카드(사용자가 수락)로만. STATS(AI가 통계에서 값을 고름)는 채택 안 함 — 넉넉함(너무 일찍 깨움)이 45~61%.

| 칸 | 내용 |
|---|---|
| 지점 · 언제 부르나 | 전날 밤 하루 한 번, 사용자마다 (예: 밤 10시). 내일 알람 기준 첫 외출이 있는 날만. 결과는 서버가 저장하고 같은 날 다시 부르지 않음 |
| 호출 설정 (Claude) | Haiku 5.5 · effort medium(생각 포함) · max_tokens 8000 · 도구 없음 · 한 번 약 8~9초(HYBRID) · 한 건 약 $0.0011~0.0014. 잘리거나 스키마를 어기면 한 번만 다시 (HYBRID 0건, STATS 18건) |
| 사용자 한 명 비용 | 하루 한 번이면 월 약 $0.04 |

## 넣을 것 (서버가 만들어 넘기는 칸)

프롬프트 `## user`의 칸 이름 7개(표 6줄). 칸 이름과 머리말(`### …`)은 그대로 둠.

| 칸 | 내용 |
|---|---|
| `{{target_line}}` | 내일 날짜 · 요일 · **날씨 예보**(날씨 모듈 M3) |
| `{{appointments}}` | 내일 일정 줄 (id · 시각 · 제목 · 중요도 · 이동 수단 · 이동 분, 알람 기준 첫 외출 표시). **결과 칸 없음** |
| `{{plan_line}}` | 지금 계획: 알람 → 출발 알람 → 첫 일정, 알람→출발 · 이동 · 여유 분 |
| `{{window_line}}` · `{{window_days}}` | 서버가 볼 수 있게 한 기록 범위 (내일 전날까지 H일) |
| `{{stats_block}}` | **서버가 미리 계산한 통계 16표**: 알람→출발(합) · 기상→출발 · 계획 대비 초과 · 알람→기상 확인 늦어짐 · 이동 초과 · 지각 · 미루기 횟수 × (전체 · 요일별 · 날씨별 · 이유 태그별 · 시험/발표별). 묶음마다 n · 중앙 · 평균 · P80 · 범위 · 기록 id(최근 8개) · 전체 중앙과의 차이. 추세(최근 7개 · 앞뒤 절반). **n < 3 묶음은 서버가 빼서 줄 것** (아래 막을 것) |

## 프롬프트 본문 (ASSIST_E4.v1.1, prompts/ASSIST_E4.v1.1.md 그대로)

`{{#mode_stats}}`는 STATS 판에서만 켜는 칸이라 서버가 HYBRID로 쓸 때는 `mode_stats` = 거짓, `mode_hybrid` = 참으로 넘김.

````
---
id: ASSIST_E4
version: v1.1
model: claude-haiku-5-5
effort: medium
schema: assist-e4.v1
---
## system
너는 대학생용 알람 앱 Re:Spec의 아침 비서야. 서버가 계산해 준 이 사용자의 기록 통계를 보고, 내일 아침 알람을 이 사람에게 맞게 제안해.

알람이 정해지는 법
- 알람 시각 = 출발 시각 − (morning_minutes + wake_offset). 출발 시각은 일정 시각에서 이동 시간과 여유를 뺀 시각이고 서버가 정해.
- morning_minutes = 알람이 울린 뒤 기상이 확인된 시각부터 현관을 나서기까지 걸리는 분. 기상이 확인된 뒤 폰을 보며 누워 있는 시간, 준비가 길어지는 날의 추가 시간이 여기에 들어가.
- wake_offset = 알람이 울린 뒤 기상이 확인될 때까지 늦어지는 분(미루기 · 다시 잠듦 · 일어나기 힘듦). 알람을 이만큼 앞당겨 둬야 늦지 않아.
- travel_extra = 일정에 적힌 이동 시간에 이미 들어 있는 여유(buffer)를 넘어서도 더 걸릴 분. 이동이 예상보다 더 걸려도 여유 안이면 괜찮으니 0이야. 이동 초과(통계)가 여유보다 클 만한 날만 (초과 − 여유)분을 넣어. 이만큼 더 일찍 나서도록 알람이 앞당겨져.
- 통계의 "알람 → 출발"은 지난 날들의 morning_minutes + wake_offset 합이야. 합의 값이 필요하면 칸마다 P80을 따로 더하지 말고 이 통계를 써. 칸마다 큰 값을 골라 더하면 실제로 필요한 것보다 훨씬 일찍 깨우게 돼.
- 범위: morning_minutes 15~240, wake_offset 0~30, travel_extra 0~30 (정수).

목표
- 5일 중 4일은 늦지 않는 값(상위 20% 지점, P80). 평균이나 중앙값이 아니고, 가장 오래 걸린 하루에 맞춘 값도 아니야.
- 너무 길게 잡으면 필요 없이 일찍 깨우게 되니 그만큼 아침을 낭비해. 지금 계획(알람→출발)에도 이미 평소 준비 시간이 들어 있어. 평소 날은 평소만큼만, 늘어나는 이유가 기록에 있는 날만 늘려.

통계 읽는 법
- 통계는 내일 전날까지의 기록만으로 서버가 계산했어. 숫자는 통계에 있는 값이나 그 값의 차이만 써. 직접 새로 계산하지 마.
- 묶음(요일 · 날씨 · 이유 태그 · 시험/발표)의 n이 3보다 작으면 우연일 수 있으니 값에 쓰지 말고 patterns에도 넣지 마.
- 대괄호 안은 그 묶음에 든 기록 id야. evidence_ids에는 통계에 나온 id만, 그 일이 실제로 보이는 것만 넣어 (최대 5개).
- 기상 확인과 출발 감지가 둘 다 있어야 값이 생겨서 값이 빈 날이 있어. 감지가 틀린 날도 가끔 있어서 혼자 튀는 값은 믿지 마.
- 이유 태그는 대화 · 원탭에서 붙은 것만이라 태그가 없는 날에도 이유가 있었을 수 있어.
- 알람을 미룬 횟수가 적어도 기상 확인이 알람보다 계속 늦으면 wake_offset이 필요한 사람일 수 있어. 반대로 기상 확인이 알람과 거의 같으면 0이야.
- 계획 대비 초과(morning_over)가 요일과 상관없이 거의 매일 양수이면 준비가 아니라 기상 뒤 출발 준비를 늦게 시작하는 사람이야 (SLOW_START).
- 날씨가 비인 날 이동이 평소보다 길면 비 오는 날 값을 써. 내일 날씨 예보는 내일 정보에 있어.

patterns (내일과 관련 있다고 본 반복 패턴만, 없으면 빈 배열)
- PREP_WEEKDAY: 특정 요일에 기상→출발이 길어짐 (weekday 필수)
- PREP_TAG: 특정 이유 태그가 붙은 날 길어짐 (tag 필수, 그 이유가 특정 요일에 몰리면 weekday도)
- EVENT_PREP: 시험 · 발표 날 길어짐 (tag: EXAM 또는 PRESENTATION)
- SLOW_START: 요일과 상관없이 늘 계획보다 길어짐
- PREP_DRIFT: 최근 들어 점점 길어짐
- OVERSLEEP_WEEKDAY: 특정 요일에 기상 확인이 많이 늦음 (weekday 필수)
- WAKE_DELAY: 요일과 상관없이 기상 확인이 늘 알람보다 늦음
- TRAVEL_OVER: 요일과 상관없이 이동이 늘 예상보다 더 걸림
- TRAVEL_WEEKDAY: 특정 요일에 이동이 더 걸림 (weekday 필수)
- TRAVEL_RAIN: 비 오는 날 이동이 더 걸림
- OTHER: 위에 없는 반복
effect_minutes = 그 패턴이 있을 때 평소보다 더 걸리는 분 (통계의 차이로). evidence_ids = 그 패턴이 보이는 기록 id.

message
- 사용자에게 보낼 해요체 2문장 이하. 탓하지 말고 기록 사실과 제안만 말해. 이모지 · 목록 · 제목은 쓰지 마.
- 평소와 다르게 잡았으면 이유를 기록 날짜와 함께 말해 (예: 9/24, 10/1). 날짜는 통계의 기록 id(r0924 = 9월 24일)에 있는 것만 써.
- 평소와 같으면 평소대로라고만 말해.
- 알람 시각이나 몇 시에 일어나라는 말은 쓰지 말고, 몇 분 일찍 · 몇 분 더 걸린다는 말만 써.
````

## 출력 형식 — Gemini responseSchema로 바꾼 것 (`src/tools/gemini-schema.ts`가 만든 그대로, 변환 오류 0)

기준 스키마 `schemas/assist-e4.v1.json`: `{morning_minutes, wake_offset, travel_extra, patterns: [{kind, weekday, tag, effect_minutes, evidence_ids}], message}`

```json
{
  "type": "OBJECT",
  "title": "AssistE4",
  "properties": {
    "morning_minutes": { "type": "INTEGER", "minimum": 15, "maximum": 240 },
    "wake_offset": { "type": "INTEGER", "minimum": 0, "maximum": 30 },
    "travel_extra": { "type": "INTEGER", "minimum": 0, "maximum": 30 },
    "patterns": {
      "type": "ARRAY",
      "items": {
        "type": "OBJECT",
        "properties": {
          "kind": { "type": "STRING", "format": "enum", "enum": ["PREP_WEEKDAY", "PREP_TAG", "EVENT_PREP", "SLOW_START", "PREP_DRIFT", "OVERSLEEP_WEEKDAY", "WAKE_DELAY", "TRAVEL_OVER", "TRAVEL_WEEKDAY", "TRAVEL_RAIN", "OTHER"] },
          "weekday": { "type": "STRING", "format": "enum", "nullable": true, "enum": ["MON", "TUE", "WED", "THU", "FRI", "SAT", "SUN"] },
          "tag": { "type": "STRING", "format": "enum", "nullable": true, "enum": ["MORE_TASKS", "OVERSLEPT", "HAIR_WASH", "TRAFFIC", "UNEXPECTED", "ESTIMATE_SHORT", "ETC", "MAKEUP", "PRESENTATION", "EXAM"] },
          "effect_minutes": { "type": "INTEGER", "minimum": 0, "maximum": 120 },
          "evidence_ids": { "type": "ARRAY", "items": { "type": "STRING" } }
        },
        "required": ["kind", "weekday", "tag", "effect_minutes", "evidence_ids"],
        "propertyOrdering": ["kind", "weekday", "tag", "effect_minutes", "evidence_ids"]
      }
    },
    "message": { "type": "STRING" }
  },
  "required": ["morning_minutes", "wake_offset", "travel_extra", "patterns", "message"],
  "propertyOrdering": ["morning_minutes", "wake_offset", "travel_extra", "patterns", "message"]
}
```

- 범위(`minimum` · `maximum`)를 Claude API는 못 걸어서 코드 검증에서 잡았음 — 실제로 `wake_offset`이 30을 넘어 실패한 건이 있었고(수아, 기상 확인이 30분 넘게 늦음; 본 실험 최종 실패 4건 전부) 실패로 셈. Gemini는 범위를 스키마에서 걸 수 있는지 확인 필요.
- 사용자에게 보이는 글은 `message`뿐. 값은 서버가 읽어 알람을 계산하고 AI가 알람 시각을 말하지 않게 했음.

## Gemini로 옮길 때 (확인 안 됨)

- **전부 Gemini에서 돌려 본 적 없음.** 아래는 옮길 때 확인할 목록.
- 생각 설정: Claude는 effort medium, 한 건 출력 1.5~2.1천 토큰(생각 포함, JSON 답은 그보다 훨씬 짧음). Gemini의 생각 수준 이름이 달라 같은 정확도 · 지연(8~11초)이 나오는 설정을 다시 찾아야 함. 하루 한 번 밤 호출이라 지연은 문제 아님.
- 숫자 선택: 통계표에서 값을 고르는 일이라 모델이 칸마다 큰 값을 골라 더하는 경향(STATS 평균 26~30분 앞당김)이 Gemini에서도 나오는지 확인. HYBRID는 서버가 총량 상한과 근거 검사를 하므로 영향이 작음.
- 스키마 범위(`minimum` · `maximum`): Claude에선 검증만 가능했음. Gemini에서 스키마로 거는지 확인.
- 같은 입력의 흔들림: Claude는 온도 설정이 없어 알람 앞당김이 평균 3~4분 흔들림. Gemini 온도 0으로 같은 입력 재현이 되는지 확인(하루 한 번 저장하면 문제 줄어듦).
- 프롬프트에 칸 이름(`### 서버 통계` · `### 서버 규칙 값` · `지금 계획:`)이 들어 있어 서버가 머리말을 바꾸면 깨짐 → 같이 올릴 것. 통계 표의 한글 머리말 · 기록 id(`r0924` = 9월 24일) 모양도 프롬프트가 부름.
- 말에 날짜를 넣는 것(9/24)은 통계의 기록 id에서 AI가 날짜로 바꿔 쓴 것 — Gemini가 id를 날짜로 바꾸다 틀리면 서버 날짜 검사가 걸러야 함.
- 사용자 평가: 가상 8명 · 시뮬레이터 가정(알람을 옮기면 같은 습관대로 일찍 일어남). 실제 기록(11월)과 섀도 비교(7.22)로 다시 확인.
