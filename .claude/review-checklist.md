# 리뷰 체크리스트 (레포 전용)

`pr-review` 스킬로 기본 검수를 한 뒤, 이 레포에서만 필요한 항목을 추가로 확인합니다. 해당 없는 항목은 건너뜁니다.

## 깊이 (스킬 Step 0)

작성자가 아니라 바뀐 내용으로 정함. 아래 위험 경로를 하나라도 건드리거나 파일 15개 · 500줄 이상이면 "깊게", 파일 3개 · 100줄 이하이고 위험 경로가 없으면 "빠름", 그 밖은 "기본". 애매하면 깊은 쪽.

- 로그인 · 세션: `mobile/src/lib/auth*`, `mobile/src/lib/supabase*`, `supabase/functions/_shared/auth.ts`
- 접근 규칙 · 스키마: `supabase/migrations/**` (RLS · 정책 · 트리거 · `pg_cron`)
- 서버 함수: `supabase/functions/**`, `supabase/config.toml`
- 알람 예약: `mobile/modules/alarm-core/**`, `mobile/src/features/alarm/**`, 예약 · 취소 · 기록 올리기를 부르는 앱 코드
- CI · 배포: `.github/workflows/**`, `.github/scripts/**`, `wrangler.jsonc`, `eas.json`
- 비밀값 · 환경 변수: `.env*` · `.env.example`, `EXPO_PUBLIC_` 변수를 더하는 코드

## 규칙

- PR 제목 `[파트] [유형] 작업 내용`, 본문 `Closes #이슈번호`, 브랜치 `유형/이슈번호-파트-설명`
- 이슈 범위 밖 파일을 고쳤다면 이유가 PR에 적혀 있는지
- 여럿이 같이 고치는 파일(`package.json`, 잠금 파일, `app.json`, DB 마이그레이션)이 다른 작업과 섞여 있지 않은지

## 앱 (Expo · React Native)

- 새 패키지가 `npx expo install`로 SDK 57에 맞는 버전으로 들어갔는지
- 폰 전용 기능(알람 · 알림 · 네이티브 모듈)을 웹에서 부르면 깨지므로 `.web.ts` 대체 파일이나 `Platform` 분기가 있는지
- 네이티브 모듈 · 플러그인 · `app.json` · 네이티브 패키지 변경이면 "APK 다시 받기 필요"가 PR에 적혀 있는지, PR 본문에 그 브랜치의 안드로이드 빌드 검사 성공 실행 링크가 있는지 (없으면 "확인 필요"로 올림. 빌드 검사는 손으로만 돌아서 링크가 유일한 근거)
- 새 권한(permissions)에 필요한 이유가 있는지
- 화면을 바꾼 PR에 캡처가 있는지

## 데이터 · 서버 (Supabase)

- 스키마 변경은 마이그레이션 파일로만 했는지
- 새 테이블에 RLS가 켜져 있고 정책이 있는지
- `service_role` 키나 외부 API 키가 앱 코드 · `EXPO_PUBLIC_` 변수에 들어가지 않았는지
- 테이블 · 칼럼 이름이 설계 문서와 같은지 (설계 문서가 레포에 있을 때)
- 서버 함수(`supabase/functions/**`)는 `pr-review` 스킬의 `supabase-edge-check.md`로 봄

## 알람

- 기상 시각 역산 · 알람 강도처럼 시각을 계산하는 로직이 바뀌었으면 테스트가 있는지
- 시간대(Asia/Seoul), 자정 넘김, 반복 알람, 미루기 횟수 처리
- 예약 · 폰 ↔ 서버 맞추기 · 울림 기록은 `pr-review` 스킬의 `alarm-scheduling-check.md`로 봄
- 네이티브 알람 코드(Kotlin · 매니페스트)는 `pr-review` 스킬의 `android-native-check.md` 항목으로 봄

## 방향성 (스킬 Step 5a에서 읽을 곳)

## 기능 흐름 PR — 작업자가 직접 확인

앱 안에서 기능이 흘러가는 길은 작업자가 알고 넘어가야 함. 그래서 이런 PR은 흐름과 판단 근거를 보여 주고, 작업자가 확인한 뒤 머지함.

- 해당: 사용자 행동이나 시각이 화면 → 함수 → 저장 · 알람 · 알림 · 서버로 이어지는 길을 만들거나 바꾸는 PR. 상태가 넘어가는 규칙(울림 → 미루기 → 해제, 약속 → 역산 → 예약, 기상 확인 등)이나, 앱 동작을 바꾸는 서버 함수 · DB 트리거 포함
- 해당 아님: 디자인 값 · 부품 모양만, 문서 · CI · 설정, 동작이 그대로인 리팩토링
- 애매하면 해당으로 봄

해당이면 보고에 두 칸을 더함 (머지 판단 바로 뒤):

1. 기능 흐름 — **작업자가 미리보기에서 그대로 따라 하며 확인하는 순서**로 씀. 코드 설명이 아니라 "어느 화면에서 무엇을 누르면 무엇이 보이는지"
   - 맨 위에 시작 주소 한 줄: 이 PR의 Cloudflare 미리보기(PR에 달린 Cloudflare 댓글의 Preview URL, 보통 `https://<브랜치 이름에서 / 를 - 로 바꾸고 소문자>-respec-alarm-capstone.vmgfh878.workers.dev`) + 경로 + `?mode=mock`. 화면 번호 목록은 `/dev/screens?mode=mock`
   - 한 단계 = `화면 번호(이름) → "누르는 것" → 보이는 것` 한 줄. 버튼 · 탭 · 토스트 · 화면 글자는 코드에 있는 글자 그대로 따옴표로. 지어내지 않음
   - 이 PR이 새로 만든 단계는 "(새로)", 바꾼 단계는 "(바뀜)". 실패하면 화면에 무엇이 뜨는지도 한 줄로
   - 함수 이름 · 파일:줄 · 상태 이름은 흐름 줄에 넣지 않음 (판단 · 근거 표 · 발견 사항에만)
   - 주소를 다시 열면 가짜 데이터가 처음으로 돌아감 → 한 묶음 안에서는 화면 안 버튼 · 브라우저 뒤로만 쓰게 적음. 흐름이 여러 갈래면 묶음(소제목)으로 나눔
   - 웹 미리보기에서 못 보는 단계(실제 알람 울림 · 푸시 · 서버 · 실기기)는 맨 끝에 "웹에서 못 봄: … — 이유" 한 줄로 따로
   - 예:
     ```
     시작: https://feat-30-fe-home-alarm-screens-respec-alarm-capstone.vmgfh878.workers.dev/dev/screens?mode=mock
     1. 화면 목록 → "H07 알람 울림 · 기상" → "일어날 시간이에요" · "8:00"
     2. (새로) H07 → "알람 해제" → H08 기상 확인, "오전 8:00에 해제 · 10분 동안 화면 사용을 보고 있어요"
     3. (새로) H08 → "폰을 보며 일어나기" → "기상 확정 · 오전 8:10", 버튼 "캡스톤팀 기상 현황 보기"
     웹에서 못 봄: 실제 소리 · 진동 — 알람 코어(네이티브)
     ```
2. 판단 · 근거 — PR이 정한 값 · 규칙 · 분기(시간 · 횟수 · 기본값 · 순서 · 실패 때 동작)를 표로: 판단 / 근거 / 확인. 판단 칸도 화면에서 보이는 말로("미루기 시간은 5 · 10 · 15분"), 코드 위치는 근거 · 확인 칸에
   - 근거: 레포 문서면 `파일 경로` + 절 제목, 이슈면 번호, 스키마면 마이그레이션 파일 · 줄. 레포 밖 문서(상세설계서 등)면 문서 이름 · 장 · 절
   - 확인: 레포 안 근거는 열어서 실제로 그렇게 적혀 있는지 봄 → 맞음 / 다름(발견 사항으로) / 레포 밖이라 확인 못 함
   - 근거가 없으면 "근거 없음 — 작성자 판단"으로 적음. 근거를 지어내지 않음
   - PR 본문의 "기능 흐름 · 판단 근거" 칸이 비었거나 코드와 다르면 발견 사항으로

머지 판단은 코드 문제가 없어도 "흐름 확인 후 머지"로 적고, 보고 맨 마지막 줄에 `<!-- flow-check:required -->`를 그대로 넣음 (보이지 않는 표시).

- 이 표시가 있으면 워크플로(`.github/scripts/flow-check.js`)가 `흐름 확인 필요` 라벨과 "흐름 확인" 검사(대기)를 붙이고, PR 본문에 확인 줄이 없으면 붙임
- 작업자가 PR 본문의 "흐름 · 판단 근거를 작업자가 직접 확인했어요"를 체크하면 검사가 통과함. 이 줄은 작업자만 체크하고 Claude는 건드리지 않음

## 보고

- 한국어로, 심각도 순으로, 파일:줄을 붙여서
- 첫 줄에 개수: "고칠 것 N · 확인 필요 N · 원래 있던 문제 N · 깊이 …". 없으면 "고칠 것 없음"
- 스타일만의 지적(줄 바꿈 · 이름 취향 · 주석 말투)은 넣지 않음. 같은 종류는 한 줄에 위치를 모음. 이 PR이 만들지 않은 버그는 [원래 있던 문제]로 따로, 머지 판단에 넣지 않음
- 순서: 한 줄 요약 → 머지 판단 → (기능 흐름 PR이면) 기능 흐름 · 판단 근거 → 방향성 → 발견 사항 → 자가 검수 → 건너뜀
