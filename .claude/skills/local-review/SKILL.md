# 로컬 리뷰

Actions의 Claude 자동 리뷰(`.github/workflows/claude-review.yml`)와 같은 기준(`pr-review` 스킬 + `.claude/review-checklist.md`)으로 검수함. 다른 점은 둘.

- 로컬 Claude Code 구독으로 돌아서 Actions 분을 안 씀
- 검수 의견을 그대로 붙이지 않고, 직접 확인해서 거른 결과만 댓글 하나로 남김. 그 뒤는 머지 판단대로 처리함 (아래 "5. 판단대로 처리" — 지형 PR에만, 10/17 지형 결정)

대상 = 워크플로 세 파일(`claude-review.yml` · `claude.yml` · `flow-check.yml`)의 `fromJSON('[...]')` 목록에 있는 사람의 PR, 지금 `vmgfh878-art`. 목록에 없는 사람의 PR은 Actions 리뷰가 돌기 때문에 이 스킬을 쓰지 않음.

자동으로 시작되는 건 작업자 개인 설정의 훅이 `gh pr create` 직후 안내할 때뿐임. 웹 · 다른 기기에서 연 PR, 나중에 `[WIP]`를 뺀 PR, 초안에서 준비 완료로 바꾼 PR은 "로컬 리뷰해줘 #N"으로 부름.

## 0. 대상 확인 · 깊이

```bash
gh pr view <N> --json number,title,isDraft,author,baseRefName,headRefName,headRefOid,files,labels,body,comments,url,additions,deletions
```

- 건너뜀: 초안 · 제목 `[WIP]` · 바뀐 파일이 전부 `.md` 또는 `docs/` 아래 (Actions 리뷰와 같은 기준). 리뷰를 돌렸는지 PR에서 보이게 한 줄 댓글을 남김: `로컬 리뷰 건너뜀 — <이유>` + `<!-- local-review:skipped -->`. 초안 · `[WIP]`는 준비 완료로 바뀌면 다시 부름
- `comments`에 로컬 리뷰 댓글(`<!-- local-review -->`)이 이미 있으면 다시 돌리지 않음 (아래 "다시 리뷰")
- 작성자가 목록에 없으면 하지 않음
- 깊이를 정함 (`pr-review` Step 0, 위험 경로는 체크리스트 "깊이"). 작성자가 아니라 바뀐 내용으로 정함
  - 빠름: 파일 3개 · 100줄 이하이고 위험 경로 없음
  - 기본: 그 밖
  - 깊게: 위험 경로를 하나라도 건드림, 또는 파일 15개 · 500줄 이상

## 1. 검수 — 새 서브에이전트

PR을 만든 세션의 맥락이 섞이지 않게 `Agent`(general-purpose)에 맡김.

- 빠름 · 기본: 서브에이전트 하나
- 깊게: 영역별로 나눠 최대 3개를 한 번에 (예: 서버 함수 · 앱 화면 · 알람 예약). 각자 자기 파일 목록만 받고, 정리(2단계)에서 합침. 영역이 하나뿐이면 하나
- 작업 폴더: 지금 폴더가 PR 브랜치면 그대로. 아니면 읽기 전용으로 `git fetch origin <headRefName>` → `git worktree add --detach ../respec-review-<N> <headRefOid>`, 3단계 댓글까지 남긴 뒤 `git worktree remove ../respec-review-<N>`
- 서브에이전트 프롬프트 (빈칸 채움):

```
REPO: 403-forbidden-capstone/respec-alarm-capstone
PR 번호: <N> / 제목: <title> / 기준 브랜치: <base>
작업 폴더: <path> (PR 브랜치가 체크아웃되어 있음)
깊이: <빠름 | 기본 | 깊게> — <이유>
맡은 범위: <전체 | 영역 이름 + 파일 목록>

이 PR을 검수하고 결과를 메시지로 돌려줘. 파일 수정 · GitHub 댓글 · 커밋 · push는 하지 않음.
1. `pr-review` 스킬로 기본 검수 (위 깊이대로, 맡은 범위만). 브라우저 · Lighthouse · 이중 빌드가 필요한 항목은
   "건너뜀: 사유". 4단계 표에서 조건이 맞는 검사 파일만 읽음
2. `.claude/review-checklist.md`의 레포 전용 항목. 기능 흐름 PR(체크리스트 기준, 애매하면 해당)이면
   "기능 흐름 · 판단 근거" 칸을 체크리스트 형식대로 (레포 문서 근거는 열어서 실제로 맞는지 확인,
   없으면 "근거 없음 — 작성자 판단"), 머지 판단은 "흐름 확인 후 머지"
3. 방향성: 스킬 Step 5a — 연결 이슈, 이 코드 위에 올라갈 열린 이슈 · PR, docs/ · 스키마와 부딪히는 곳.
   작은 수정이면 "방향성: 해당 없음 — 이유" 한 줄
4. 자가 검수: 스킬 Step 5b (references/self-check.md)
5. 지적 쓰는 법 (스킬 Step 6): 스타일만의 지적은 빼고, 같은 종류는 한 줄에 위치를 다 모으고
   ("같은 종류: 파일:줄 외 N곳"), 이 PR이 만들지 않은 버그는 [원래 있던 문제]로 표시
6. 돌려줄 것 (한국어): 한 줄 요약 / 머지 판단(머지 가능 · 흐름 확인 후 머지 · 수정 후 머지 · 막힘) /
   기능 흐름 PR 여부 / 기능 흐름 · 판단 근거 / 방향성 / 발견 사항(심각도 · 파일:줄 · 근거 · 같은 종류 위치 ·
   원래 있던 문제 여부) / 자가 검수 / 건너뛴 항목 / `/code-review ultra` 추천 여부와 이유
   (추천 기준: 깊게, 또는 확신 낮은 발견 여럿)
```

## 2. 의견 정리

- 발견마다 해당 줄을 직접 열어 맞는지 확인 → 틀린 지적은 뺌 (댓글엔 뺀 개수만)
- 서브에이전트가 여럿이면 같은 지적은 하나로 합침
- 남은 지적을 셋으로 나눔
  - 고칠 것: 판단이 필요 없는 확실한 문제 (오타 · 명백한 버그 · 틀린 문서 경로 · 타입 오류)
  - 확인 필요: 기능 · 화면 · 기술 판단이 걸린 것 (결정은 작업자 · 팀)
  - 원래 있던 문제: 이 PR이 만들지 않은 버그. 머지 판단에 넣지 않음
- 고치는 건 5단계 판단대로만 (수정 후 머지일 때 "고칠 것"만). "확인 필요"는 작업자 · 팀이 정할 때까지 고치지 않음
- 서브에이전트를 다시 부르지 않음 (리뷰는 1번)

## 3. 댓글 하나

임시 파일에 쓰고 `gh pr comment <N> --body-file <파일>`. 줄 단위 댓글은 달지 않음. 순서는 체크리스트 "보고"와 같게.

```markdown
## 로컬 리뷰

**머지 판단: <머지 가능 | 흐름 확인 후 머지 | 수정 후 머지 | 막힘>** — 고칠 것 N · 확인 필요 N · 원래 있던 문제 N · 깊이 <빠름 | 기본 | 깊게>
<한 줄 요약>

### 기능 흐름 · 판단 근거
<기능 흐름 PR만. 체크리스트 형식 그대로>

### 방향성
- <다음 이슈 · 문서 · 스키마와 부딪히는 곳, 근거와 함께>

### 고칠 것
- [높음 | 중간 | 낮음] <무엇> (`파일:줄`) — <근거>. 같은 종류: `파일:줄` 외 N곳

### 확인 필요
- [높음 | 중간 | 낮음] <무엇> (`파일:줄`) — <이유 · 선택지>

### 원래 있던 문제
- <무엇> (`파일:줄`) — <언제부터 · 이 PR과의 관계>

<details><summary>자가 검수 · 건너뛴 항목</summary>

- <다시 확인한 것 · 뺀 지적 N개 · 이 환경에서 못 본 것>

</details>

<sub>로컬 Claude Code · pr-review + 레포 체크리스트 · 기준 커밋 <headRefOid 앞 7자리> · <N>번째 리뷰</sub>
<!-- local-review -->
```

- 빈 칸은 지움 (기능 흐름 PR이 아니면 그 칸 통째로, "원래 있던 문제"가 비면 통째로, "고칠 것" · "확인 필요"가 비면 "없음"). 고칠 것이 없으면 요약 줄에 "고칠 것 없음"이라고 그대로 씀
- 같은 종류가 없으면 "같은 종류" 부분은 뺌
- `/code-review ultra` 추천 대상이면 방향성 아래 한 줄: "더 깊은 검수가 필요하면 로컬에서 `/code-review ultra <N>` — 이유: …" (실행은 작업자)
- `<!-- flow-check:required -->`는 넣지 않음 (그 표시는 봇 댓글만 읽음. 라벨은 4단계에서 직접 붙임)

## 4. 기능 흐름 PR 표시

Actions의 "흐름 확인" 검사는 이 PR에서 돌지 않으므로 표시만 붙임.

- `gh pr edit <N> --add-label "흐름 확인 필요"`
- PR 본문에 확인 줄이 없으면 끝에 붙임 (`gh pr edit <N> --body-file`): `- [ ] (기능 흐름 PR만) 흐름 · 판단 근거를 작업자가 직접 확인했어요` (`.github/scripts/flow-check.js`의 `CHECK_LINE`과 같은 글자)
- 이 줄은 작업자만 체크함. "흐름 확인" 상태 검사는 만들지 않음

## 5. 판단대로 처리

지형(`vmgfh878-art`)이 연 PR에만 적용함 (10/17 지형 결정). 다른 사람 PR이면 댓글까지만 하고 끝.

- 수정 후 머지: "고칠 것"을 같은 PR에서 고침 (`mobile/`에서 `npm run typecheck` · `npm run lint` · `npm test`, 서버 함수면 `deno test`, 파일 지정 `git add`). 커밋 메시지에 고친 지적을 적고 push, 리뷰 댓글 아래에 고친 커밋을 한 줄로 남김. 고친 뒤 머지 판단은 남은 지적으로 다시 정함: 남은 게 없고 기능 흐름 PR이 아니면 머지 가능, 기능 흐름 PR이면 흐름 확인 후 머지
- 흐름 확인 후 머지: 머지하지 않음. 지형이 흐름을 보고 OK할 때까지 그대로 둠 (작업 끝에 넘기는 PR 목록에 올림)
- 머지 가능: `gh pr merge <N> --squash`
- 막힘: 머지하지 않고 채팅에 이유
- "확인 필요"가 남아 있으면 판단과 상관없이 채팅 보고에 적어 지형에게 넘김

## 채팅 보고

몇 줄: 머지 판단 · 고칠 것 개수 · 확인 필요 개수 · 처리한 것(고친 커밋 · 머지 여부) + 댓글 링크.

## 6. 작업자 반응 기록

5단계에서 고친 지적은 "고침"으로, 작업자가 이 세션에서 지적에 반응하면(틀렸어 · 일부러 그런 거야 · 안 고칠래) 그 반응으로, 지적마다 `.claude/review-log.md` 표에 한 줄을 더함. 리뷰는 이 파일을 읽지 않음. 헛지적이 얼마나 되는지 세는 용도임.

- 반응: 고침 / 틀림 / 의도 / 안 고침
- "틀림" · "의도"가 다음에도 나올 종류면 `.claude/pr-review-learnings.md`의 "지적하지 않을 것"에 한 줄 더할지 작업자에게 물음 (묻지 않고 넣지 않음)
- 이 두 파일만 바뀐 커밋은 해당 PR에 같이 넣거나, 따로 모아 문서 PR로 올림. 커밋 · push는 작업자 확인 뒤

## 다시 리뷰

작업자가 "다시 리뷰"라고 할 때만. 스스로 다시 돌리지는 않음 — 특히 지난 판단이 "흐름 확인 후 머지" · "머지 가능"이면 작업자 확인 · 머지로 끝.

- 볼 범위는 새 diff만: 지난 로컬 리뷰 댓글의 "기준 커밋"부터 지금까지 (`git diff <기준 커밋>..<headRefOid>`). 깊이도 그 diff로 다시 정함
- 서브에이전트 프롬프트에 더함: "지난 로컬 리뷰 댓글(<링크>)의 지적마다 상태(고침 / 남음 / 작성자가 닫음)를 한 줄로. 지난 지적을 다시 풀어 쓰지 않음. 새 diff가 건드리지 않은 코드의 새 발견은 [원래 있던 문제]"
- 댓글 맨 위에 "지난 지적" 칸(상태 한 줄씩)을 두고, 그 아래 새 지적만
- 이 PR의 3번째 리뷰부터는 요약 줄 첫마디를 "방향을 다시 볼지" 질문으로 씀 (리뷰를 더 돌리기보다 접근을 바꿀 때일 수 있음)
- 새 댓글 하나를 남기고 지난 댓글은 고치지 않음
