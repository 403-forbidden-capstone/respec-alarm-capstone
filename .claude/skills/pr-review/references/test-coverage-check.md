# Test coverage check

Research on code review effectiveness consistently names this as a blind spot distinct from finding bugs directly: a reviewer checks that the logic looks right and approves, without separately asking whether anything now guards that logic against regressing later. This is especially costly on a bug-fix PR — the bug existed because some input/timing/edge case wasn't handled, and if the fix isn't paired with a test for that exact case, the same class of bug has a real chance of coming back the next time someone touches the same code, with nothing to catch it before it ships again.

## When to run this

Triggered on every PR that changes non-trivial logic (not pure CSS/copy/config changes) — but weight it especially heavily when: the PR is a bug fix (check whether the specific input/condition that caused the bug now has a regression test); the PR adds a new branch/conditional to existing logic (check whether both the new branch and the existing ones it might interact with are covered); the PR touches a file that already has a test file alongside it (the convention is established in this repo — a change with no matching test update is a gap, not a stylistic choice); the PR fixes a bug that came from two pieces of logic disagreeing with each other (check specifically that a test now pins down the invariant that was violated, not just the one function's fixed behavior).

## How to check it

1. **For a bug-fix PR, find the specific input or condition that triggered the bug and check whether a test now exercises exactly that.** Read the bug description/commit message, extract the concrete trigger (a specific value, a specific sequence of calls, a specific timing), and grep the test files changed in the diff (or the ones that should have been) for a test naming or exercising that trigger. A fix with no test for its own trigger condition is the single highest-value finding in this category — it means the exact bug that was just found and fixed has no guard against silently returning.
2. **For a new branch in existing logic, check both the new path and whether it could break a path that already had a test.** A new `if` added to a function that already has test coverage needs its own test case, and the existing tests need a quick check that the new branch doesn't accidentally make one of them pass for the wrong reason (the new condition swallowing a case the old tests relied on).
3. **When a PR's own commit message describes fixing a divergence between two related functions/files** (the same concept implemented twice, now brought back in sync), check whether the test suite has anything that would have caught them diverging *before* this PR, or whether the fix only adds a test for the one function that was reported — leaving the sibling free to drift again with nothing to notice. If there's a way to write one shared test/invariant that both implementations must satisfy, that's worth naming as the deeper fix over two separate one-off tests.
4. **Boundary conditions, not just the primary case.** For new logic operating on a collection or a range (first item, last item, empty input, single-item input, a tie/equal-value case), check whether tests exist for the boundaries, not just a "normal" 3-5-item case — boundary conditions are disproportionately where real bugs hide and disproportionately absent from a PR author's own manual testing.

## Severity framing for the report

- No regression test for a bug-fix PR's own trigger condition is medium-to-high — the fix is real today, but nothing stops it from silently regressing, and the fact that it regressed once (or the class of bug recurred, as with a mislabeled-precision or unextracted-API-field bug repeating across sibling functions) is itself evidence it's likely to happen again without a test pinning it down.
- Missing coverage for a brand-new feature's core logic (not a fix) is lower urgency than a missing regression test, but still worth naming plainly rather than skipping — "no tests for X" is a one-line, low-effort finding that's easy to act on.
- Don't invent a finding here just because a PR could theoretically have more tests — only flag it where a *specific* untested input/branch/boundary can be named concretely; a vague "add more tests" isn't actionable and shouldn't be reported as if it were.
