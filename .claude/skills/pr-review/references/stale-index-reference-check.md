# Stale index-reference check

Added after a real miss: a list of course stops gets a `highlightIndex` state to track which one is highlighted on an accompanying map. The index is set on hover/tap and cleared on mouse-leave — both handled. What's missing is every *other* way the list itself can change: removing a stop, adding one, or dragging to reorder all change which item lives at which position, and none of those code paths touch `highlightIndex`. Highlight index 2 stays "2" after the item that used to be at index 2 is deleted and everything shifts up — now it points at a different, unrelated stop, which lights up on the map instead of the one the user actually meant. The bug is invisible from reading `removeStop`/`addStop` in isolation, because neither function has anything to do with highlighting — it only shows up when you ask "what holds a *position* into this list, and does every place that changes the list's *shape* know to update it?"

This is a narrower, more mechanical cousin of `derived-value-integrity-check.md`'s sibling-collections pattern: instead of two derived collections disagreeing, it's one piece of state (an index, not a derived value) whose validity silently depends on an array it doesn't actually reference or get recomputed from.

## When to run this

Triggered whenever the diff adds or keeps a piece of state that holds a *position* into a list — an index (`useState` initialized to a number or `null`, used as `array[index]`), a "current item" tracked by array position rather than by a stable id — where that same list can be added to, removed from, filtered, or reordered elsewhere in the component. Common hosts: a carousel/slideshow's current-slide index, a wizard's current-step index, a table's selected-row index, a map/canvas's highlighted-segment index (as here), a focus-management "currently focused item" tracked by position.

## How to check it

1. **Find every function that changes the list's length or order** — add, remove, filter, sort, drag-reorder, bulk-replace — and check each one against the index state: does removing/inserting before the held index shift what it now points at? Does removing the exact item the index pointed at leave it pointing at whatever happens to be there now, or past the end of the shrunk array?
2. **Prefer identity over position when the fix is cheap.** If the state can instead hold the item's stable `id` (and the index is derived on render via `list.findIndex(x => x.id === heldId)`), that sidesteps the whole class of bug — the reference stays correct automatically as the list changes shape, and it degrades gracefully (not-found → treat as "nothing selected") instead of silently pointing at the wrong thing. Suggest this as the fix over "remember to reset the index in every mutator," since the second approach only works as long as every future mutator remembers to do it too.
3. **If the index has to stay index-based** (e.g. it's tied to a positional concept like "the leg between stop N and stop N+1" rather than to any single item's identity), then every mutator of the list must explicitly reset or remap it — check that each one actually does, not just the ones the diff happened to touch. A `setState(null)` on every add/remove/reorder handler is the minimum; silently doing nothing is the bug.
4. **Check the read site's bounds handling too**, independent of the mutators: if the index ends up pointing past the new (shorter) array, does the code reading it (`array[index]`, a `.map` callback keyed off it) guard against `undefined`, or does it silently render garbage / throw? A bounds guard reduces the failure from "shows the wrong thing" to "shows nothing," which is better but still means fixing the mutators is the real fix, not a substitute for it.

## Severity framing for the report

- A stale index that silently highlights/selects/focuses the *wrong* item (rather than crashing or clearing) is medium-to-high — it's a correctness bug that looks like a working feature, so a user has no reason to suspect anything's wrong and may act on the mislabeled result (leaving the wrong stop highlighted while looking at directions for it, editing the wrong row, confirming the wrong step).
- A stale index that goes out of bounds and is read with no guard (crash, or `undefined` rendered raw) is high — same root cause, worse visible failure.
- If switching to id-based tracking is a small, mechanical change (the list items already have stable ids, which is common — check for a `key={item.id}` on the same list as a quick signal), name that as the preferred fix over enumerating every mutator that needs a reset; it's usually less code and structurally can't regress the same way again.
