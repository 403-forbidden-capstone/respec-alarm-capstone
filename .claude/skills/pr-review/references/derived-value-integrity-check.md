# Derived-value integrity check

Added after a real miss: a PR that computed per-leg distance by distributing a route's total across legs using each leg's *coordinate-point count* as the weight — vertex count has no real relationship to distance (a straight highway leg has few points; a short winding street leg has many), so the displayed per-leg numbers could be badly wrong even though the total was correct and the code read as reasonable. The same PR also rounded each leg's minutes independently before display, so leg numbers could sum to something visibly different from the trip-total header (11+11+11 shown under a "32분" header). Two turns after that, a review of the *same file* found the exact bug this PR was written to fix — a third-party API response field left unextracted, silently forcing a value to always be estimated — recurring in a sibling function (`fetchDriving` got fixed to pull `distance` from the Kakao response; `fetchTransit`, calling a different provider, was never checked for the equivalent field and still doesn't extract it). And a validation guard added to stop one bad-input crash (`hasValidCoords` filtering a stops array) was never applied to a same-shaped argument two lines away (`origin`, used the same way, unfiltered). None of these are visible reading the diff's own lines in isolation — each requires checking a number or a guard against something *outside* the immediate hunk: the real quantity it claims to approximate, the total it's supposed to sum to, a sibling function's equivalent field, or a structurally identical call site.

A fifth shape surfaced later on the same file: two `useMemo`-derived collections computed from the identical source state (`customStops`), where one (`route.stops`, via `recalcRoute`) filtered out entries with invalid coordinates and the other (`excludeIds`, straight off `customStops`) didn't. Both were meant to represent "what's currently in the course," and for any entry that got filtered by one but not the other, the two fell out of sync: the invalid entry vanished from the rendered list (so there was no UI element left to remove it) while still counting as "already in the course" for the add-modal's exclusion check (so it could never be re-added either) — a slot the user could neither see nor act on, silently consuming one of the course's spots forever. Nothing about either `useMemo` looks wrong read on its own; the bug only exists in the gap between what the two are supposed to agree on.

## When to run this

Triggered whenever the diff: distributes a total across parts using a proxy/weight variable (anything computed by dividing or apportioning a sum); displays both a total and its components in the same UI (a rounded sum next to independently-rounded parts); wraps or extends a call to a third-party/external API and extracts only some of the response fields; adds a validation guard, null check, or fallback in response to one reported input and the function has other same-shaped inputs nearby; or computes more than one derived/memoized collection (a filtered list, an id `Set`, a count) from the same source state.

## How to check it

1. **Proxy-variable distribution**: when code apportions a total (`total * (weight / totalWeight)`), ask what `weight` actually measures and whether that's the same thing the total represents. Point count, array length, or item count used as a stand-in for distance, time, or size is a red flag unless the comment gives a specific, checked reason they correlate. If the real per-part values are available from a different field in the same response (see #3 below) or a different call, prefer that over any proxy.
2. **Sum vs. displayed total**: if a total is rounded for display (e.g., `Math.round` on a sum) and the individual parts are *also* independently rounded and shown, check whether they can visibly disagree — a user comparing "3 legs, 11 min each" against a "32 min" header will notice `11×3=33≠32` even though every number is individually "correct" to its own rounding. Round the total from the unrounded parts, or round parts from a total-preserving distribution (e.g., largest-remainder method), not both independently from the same source.
3. **Underused API response fields**: when a function wraps a third-party API call, read the *actual response shape* being parsed (or the sibling function that parses a similar response), not just the fields the diff's function happens to extract. Ask specifically: does this response likely contain a field for [the value currently computed via approximation]? This is worth a few minutes checking the provider's docs or a sample response, especially when the PR's whole purpose is upgrading approximated values to real ones — leaving one still-approximated because its field wasn't extracted directly undermines that purpose. If a sibling function in the same file/PR *was* fixed to extract an equivalent field from a different provider, treat every other still-approximated value in the diff as a candidate for the same fix, not just the one that was reported.
4. **Guard/fallback rollout completeness**: when a diff adds a validation guard (`isValid(x)`, a null check, a `?? fallback`) to fix one input, grep the same function and its close neighbors for every other argument of the same shape/origin and check whether each one needs the identical guard. A guard added to a `stops` array but not to an `origin` point used the exact same way in the exact same function is the shape of gap to look for — same risk, same fix, just not copied over. The same applies to sibling display values: if one field in a rendered object got a `?? '-'`-style fallback because it can be `null`, check whether adjacent fields in the same object have the identical nullability and the identical fallback. Don't stop at the function's own file — if the guard exists because a hook/pattern shared by other components (not just other arguments) has the same risk, grep for every other consumer of that hook/pattern across the codebase, including files this diff doesn't touch. This is the same instinct as `async-migration-check.md`'s "every consumer is a separate instance, not one bug" — a fix proven necessary in one place is evidence, not just a hint, that every sibling needs the same look.
5. **Sibling derived collections from the same source.** When a diff computes more than one `useMemo`/derived value from the same base state — a filtered/validated list and a `Set` of ids, two different filtered views, a count and a list it's supposedly counting — write down in one sentence what each one is *supposed to represent*, and check whether they use the same filter/transform to get there. If one applies a validity check the other skips, name the specific input that would make them disagree (an entry the check would remove) and trace what breaks on each side: something invisible in the UI that's still "counted" elsewhere, or something counted that isn't actually shown. This is easy to miss because each `useMemo` is individually correct for what it says it computes — the bug is only visible when you hold both derivations next to each other and ask if they're allowed to diverge.

## Severity framing for the report

- A proxy-variable distribution or independent-rounding mismatch is medium-to-high severity specifically when the PR's stated purpose is *display accuracy* — the bug directly undercuts the reason the PR exists, even though nothing crashes.
- An unextracted API field that keeps a value permanently "estimated" is worth flagging as a concrete, usually-small fix (verify the field exists in a real response first, then it's often a one-line change) rather than a deep redesign — say so, since it changes how urgently it needs fixing.
- An incompletely-rolled-out guard is low-to-medium on its own (the original crash is fixed for the reported case) but should be named explicitly as "same fix, missing at this other call site" so it doesn't require a second report to find the second occurrence.
- Two sibling derivations falling out of sync is medium-to-high specifically when the divergence produces a state the user can't recover from through the UI (something removed from view but still "counted" elsewhere, blocking a re-add or a retry) — that's worse than a wrong number on screen, because there's no visible symptom pointing at the cause; the user just experiences the feature as broken with no obvious next step.
