# Interactive visualization scope check

Added after a real miss: a PR added hover-to-highlight on a map — hovering a stop in a list should bold its route segment on the map. The implementation added the highlight index to the dependency array of the map's single draw `useEffect`, which (for good reasons unrelated to highlighting) tears down every polyline/overlay and calls `map.setBounds(...)` on every run. The result: hovering each stop in the list reset the user's own pan/zoom back to the full-route view and made every line flicker, on every single hover — the feature made the map harder to use while looking, in a code review, like a reasonable one-line dependency-array addition. The same PR wired the same highlight state to both `onMouseEnter`/`onMouseLeave` and `onClick`, intending "hover on desktop, tap on mobile" — but touch devices synthesize a `mouseenter` immediately before `click` for compatibility, so a tap sets the highlight via the hover handler and then the click handler's own toggle (`current === index ? null : index`) immediately cancels it back to `null`. Tap-to-highlight silently never worked, despite the comment describing exactly that behavior. Both bugs are invisible to a static read of the changed lines — they only show up once you ask "what does this handler/effect actually *do*, every time it fires, including the times its author wasn't picturing."

## When to run this

Triggered whenever the diff adds or changes: a `useEffect` (or equivalent) that redraws/rebuilds a map, canvas, chart, or other imperative visualization, where the dependency array mixes real data (stops, paths, fetched results) with transient UI-only state (a hover index, a selection, a highlight, a drag position); or a combination of hover handlers (`onMouseEnter`/`onMouseLeave`/`onPointerEnter`) and a click/tap handler on the same element that both write to the same piece of state.

## How to check it

1. **List everything the effect body actually does, then ask which of those things should happen on every dependency, and which should only happen on a subset.** A map-draw effect typically does several distinct things — create the map instance (once), redraw geometry (when the route data changes), and reposition the camera/viewport (when the route data changes, but *not* when only a selection/highlight changes). If a UI-only value is in the dependency array, trace every statement in the effect body and flag any that mutates persistent view state (`setBounds`, `scrollIntoView`, resetting a zoom/pan, clearing and reopening something) — that statement firing on a hover is very likely wrong, even if teardown-and-redraw of the visual elements themselves is intentional and fine.
2. **When geometry legitimately needs to be redrawn on a UI-only change too** (e.g., to restyle just the highlighted segment), consider whether the diff actually needs a second, narrower effect keyed only on the UI-only state — one that restyles the already-existing shape (change stroke width/color on the specific polyline object, add/remove just one overlay) instead of tearing down and rebuilding everything. If the diff doesn't do this and instead reuses the existing full-redraw effect, that's the shape of the bug to name specifically, with the concrete side effect it triggers (viewport reset, flicker, refetch, whatever the full effect does beyond restyling).
3. **For combined hover + click/tap handlers on the same state**: check what happens on a touch device specifically, not just desktop. If `onMouseEnter` sets a value and `onClick` toggles it (`current === X ? clear : set`), trace the sequence when a touch synthesizes `mouseenter` immediately before `click` — the toggle will almost always see "already equal to X" (since the just-fired mouseenter set it) and immediately clear it, so the net effect of a tap is always "off," regardless of what the click handler's logic looks like read on its own. This is worth checking any time both event families write to the same state, not just for this exact pattern — the general question is "if a touch fires both handlers back-to-back, what's the final state, and does that match what the comment/intent says should happen?"

## Severity framing for the report

- A hover-triggered viewport/camera reset on a map or similar visualization is medium-to-high severity even though nothing is broken in a crash sense — it actively fights the user's own interaction (they zoom in, then the next hover zooms them back out), which is worse than the feature not existing, and it's exactly the kind of regression that's easy to miss in review because the diff itself looks like a minimal, reasonable change.
- A tap/touch interaction that silently never fires as intended is medium severity on its own, but should be flagged clearly as "desktop-only despite the comment/intent claiming both" — this is a case where checking the stated intent (see `error-propagation-check.md`) and checking the interaction wiring converge on the same bug from two directions.
