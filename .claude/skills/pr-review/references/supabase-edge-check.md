# Supabase Edge Function check

`backend-data-layer-check.md` covers schemas, queries, and retries in general. This file covers what is specific to this repo's server: Deno Edge Functions on Supabase that write with the `service_role` key, call Kakao, and send push. In this setup RLS does not protect a `service_role` write. The gateway setting in `config.toml` decides who can call a function at all. And there is no transaction across PostgREST calls. A line can look fine while a caller can still write to someone else's rows, or a timeout can leave half a write behind.

Found in the PR #167 review (2026-10-16, 5 functions, ~7,000 lines): a non-idempotent create (a retried request made two sets of alarms), push title and body taken from the caller and sent as-is to another user's phone, a manual value that was not carried over on re-save, and a Kakao timeout that applied per call rather than to the whole request.

## When to run this

Run it when the diff touches `supabase/functions/**`, a `[functions.*]` block in `supabase/config.toml`, or a migration that adds or changes a function, trigger, `pg_cron` job, Vault secret, or RLS policy that an Edge Function relies on. Otherwise skip it and don't read this file.

## How to check it

1. **Who can call it.** Each function has a `[functions.<name>]` block in `config.toml`. If `verify_jwt = true`, the code still confirms the user with `auth.getUser` (see `_shared/auth.ts`). If `verify_jwt = false` (server-only functions such as batches), the code compares the service key itself and fails closed when the key is missing. A new function without a block gets the default, so check that the default is what the author meant.
2. **Which client writes.** A user-scoped client is limited by RLS. A `service_role` client is not. Every `service_role` read or write needs its own owner or permission check before it, such as `sharing_permissions` for writing to another user's alarm, plus an explicit `user_id` filter. "RLS covers it" is not true on this path.
3. **Input.** A bad JSON body or a wrong type returns 400 or 422, not 500. Check time strings, IDs, list lengths, and text lengths. Text that will reach someone else (push title, body, `data`) is fixed on the server, or at least length-limited and rate-limited. It is never passed through from the caller.
4. **Retries and duplicates.** The app retries after a timeout. Creates need an idempotency key (a client-made ID, a unique constraint, or `upsert` on a natural key such as `event_key` or `client_event_id`). An update on an existing ID is safe to repeat. Check that the README and code comments claiming "same request, same state" are true for every path, not only for the update path.
5. **Partial writes.** Several PostgREST calls in a row are not a transaction. For each step, ask what state is left if that step fails and the next one never runs. Either order the steps so that what is left can be recovered (the app reconciles on start, or a batch fills the gap), or move the steps into one SQL function (RPC). An error after the main write has already succeeded should not look to the app like a failed save.
6. **Carried-over values.** On re-save, fields the caller left out keep the stored value when its source is `MANUAL`. Check every `*_source` field the same way (time, intensity, travel). One field that falls back to `AUTO` silently overwrites what the user typed.
7. **External calls (Kakao).** There is one time budget for the whole request, not a separate one per call. The abort signal also covers reading the response body. A failure has a fallback the app can show (for example, manual travel time with a warning code). Keys never appear in logs or responses. Kakao responses are not stored or reused across requests unless a repo document allows it (the API terms restrict storage).
8. **Time and "that day".** Deno runs in UTC. Any rule about a day ("first appointment that day", a daily batch at 03:00, today's group) converts to `Asia/Seoul` explicitly. A "first that day" rule compares appointment times, not alarm times.
9. **Shared calculation.** `_shared/calc` must give the same answer as the app's calculation for the same input. If the diff changes one side, check the other side and the shared test cases. If the two disagree, the phone shows one time and the server stores another.
10. **Batches and cron (`pg_cron` → `pg_net` → function).** Running the batch twice gives the same result. Each run has a bounded amount of work. The time window has no gap and no overlap between runs. The Vault secrets it needs are written down in the PR's deploy steps.
11. **Errors and CORS.** Errors use the shared shape (`_shared/errors.ts`) with status codes the app handles, and no stack traces. Functions the web calls answer `OPTIONS` through `_shared/cors.ts`.
12. **Tests and deploy.** Run `deno test` in `supabase/functions` if Deno is installed. Otherwise report "skipped: no Deno" and read the test files for the cases above. A new secret, config block, or migration order needs to be in the PR's deploy steps.
