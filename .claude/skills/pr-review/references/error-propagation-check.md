# Error propagation & stated-intent check

Added after a real miss on the same PR that prompted `async-migration-check.md`, but a different bug shape. A helper deep in a call chain (`findNearbyParking`) called a fetch wrapper (`getJson`) that throws on a non-2xx response. Nothing between that throw and the UI caught it: the function calling it had no try/catch, that function was called inside a `Promise.all()` over several legs that were each supposed to degrade independently, and the React effect consuming the final result had `.then()` with no `.catch()`. One flaky API response anywhere in that chain produced a silent unhandled rejection — the screen just froze on its loading-state fallback with no error shown. A second bug on the same PR was a different genus entirely: a comment said "the remaining segment is still added as an estimate," and the code below it simply didn't add it — the comment described the intended fix, not what shipped. Both slipped past a normal read-the-diff pass because the diff looked locally reasonable at every line; the defect only exists in the gap between what a function is supposed to guarantee and what it actually does under failure, or between what a comment claims and what the code below it executes.

This is not the same failure mode as `async-migration-check.md` (a data source's *timing* changing from sync to async, and a gate not accounting for the new loading window). This is about async code that was already async, where a *failure path* — not a slow path — falls through every layer meant to catch it, or where documentation and implementation quietly diverge. Read `async-migration-check.md` too if the diff has both shapes; they're commonly the same PR.

## When to run this

Triggered whenever the diff adds or changes an `async` function that sits in a call chain — especially when: a new function wraps a fetch/API call and is called from other async code; a `Promise.all()`/`Promise.allSettled()` batches several calls that are documented or clearly intended to degrade individually on failure; or a comment states what should happen in a fallback/edge case ("the remaining part is still estimated," "this falls back to X," "partial failures don't block the rest").

## How to check it — error propagation

1. **Find every function in the changed call chain that can throw or reject**, not just the one the diff directly touches. Read the actual implementation of anything it calls — a wrapper like `getJson`/`fetch` that throws on a bad status code is easy to miss if you only read the caller and assume "an API call failing just returns null or undefined," which is a very common but unverified assumption. Grep for `throw` in every function on the path, and check whether any awaited call is a bare `fetch`/HTTP client without a wrapping try/catch.
2. **Walk the chain upward from that throw site to wherever it's ultimately handled**, function by function. At each level ask: does this specific function catch it (try/catch around the await, or a `.catch()` on that specific promise), or does it let the rejection propagate to its own caller? A function is "safe" only if it or something above it actually catches — not if it merely happens to be inside an async function, since async functions propagate rejections by default just like they'd propagate a thrown error.
3. **`Promise.all()` is the trap worth specifically naming**: if the surrounding code's own comments or structure imply "each item should succeed or fail on its own" (a per-leg fallback, a per-item degrade), but the array of promises passed to `Promise.all()` contains one whose underlying implementation can reject rather than resolve-to-null/undefined on failure, the whole batch aborts on the first rejection — silently defeating the per-item design. This is the single highest-value pattern to check: any `Promise.all()` over calls to a function this diff just added or changed.
4. **Find the top of the chain — the actual UI consumer** — and check whether it has real error handling: a `.catch()` on the promise chain, or a try/catch around the `await`. `.then(callback)` with no `.catch()` is not safe; an unhandled rejection there is invisible to the user (no error UI, no console message a non-technical user would ever see) and typically leaves state stuck at whatever it was initialized to, which usually reads as "quietly broken" rather than "visibly failed."

## How to check it — stated intent vs implementation

Comments and docstrings in a diff are not just context to read past — treat every claim they make about behavior as something to verify against the code that follows, the same way you'd verify a function's return type against what it actually returns. This matters most for:

- **Fallback/degradation claims** ("if X fails, Y is used instead," "the remaining segment is estimated and added," "partial results still show"). Find the actual line that's supposed to implement the claim. If you can't point to it, that's a finding — the comment describes the intended design, not what shipped.
- **Labeling/provenance claims** — when a PR's whole point is distinguishing two kinds of value (measured vs. estimated, live vs. cached, verified vs. approximated), specifically hunt for any place that hardcodes the label instead of deriving it from how the value was actually computed. A pattern like `wasEstimated: false` written unconditionally right after a branch that *can* produce an approximated result is a near-guaranteed miss — the flag was probably true only for the original, simpler code path and never updated when a new approximation path was added alongside it.
- **"Only when" / "always" claims** about when a code path runs. If a comment says a fallback "only kicks in when direct lookup fails," check that the surrounding conditional actually gates on that, not on something adjacent to it.
- **Third-party API request-parameter claims** — when a diff adds/changes a parameter in a call to an external API and a comment states what that parameter does ("also gives us X"), verify it against the API's actual documentation, not just against the rest of this diff's code. A parameter can do more than the comment assumes (a flag named for what it *adds* can also silently *remove* something, e.g. a `summary: true` that both adds summary fields *and* strips per-section detail the rest of the function still reads). Checking only "does the code downstream handle what this comment says the response contains" will pass even when the comment's premise about the API itself is wrong — fetch the actual docs page for the endpoint when the diff's behavior hinges on a parameter's exact contract, don't reason from the parameter's name alone.

## Severity framing for the report

- An unhandled rejection that leaves a user-facing screen silently stuck (no error shown, state frozen at its initial/fallback value) is high severity even though it's not a crash — it's indistinguishable from the feature just not working, and nothing in the UI tells the user or a future developer why.
- A comment-vs-implementation gap on a fallback path is high severity specifically when the PR's stated purpose is accuracy/correctness (as opposed to a minor UX nicety) — the missing piece directly undermines the PR's own reason for existing, just relocated rather than fixed.
- A mislabeled provenance flag (estimated shown as measured, or vice versa) is high severity whenever the PR's feature is that exact distinction — the bug doesn't just produce a wrong number, it makes a wrong number look trustworthy.
