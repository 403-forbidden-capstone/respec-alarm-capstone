# Accessibility-in-code check

This is deliberately narrower than what `ux-review` does. `ux-review` measures a *rendered* page — real contrast ratios, real touch-target rects, real screenshots at real breakpoints — and is the right tool whenever a live page is available to test. This check exists for the code-review moment before that: reading a diff that adds a new interactive element (a modal, a dropdown, a custom button, a tab panel) and asking whether the markup and event wiring *can* be accessible at all, independent of how it looks. A `<div onClick>` with no keyboard handler and no role will still measure "fine" in most automated contrast/size checks and still be genuinely unusable without a mouse — that gap is exactly what this check is for.

## When to run this

Triggered whenever the diff adds or changes: an interactive element built on a non-native tag (`<div>`/`<span>` with an `onClick`, instead of `<button>`/`<a>`); a modal, dialog, dropdown, menu, or popover; a custom widget with multiple interactive parts (tabs, an accordion, a combobox); any element whose visual state changes without a full re-render the accessibility tree would naturally pick up (a toggle, an expand/collapse, a validation error appearing).

## How to check it

1. **Non-native interactive elements.** For every `<div>`/`<span>` (or framework equivalent) with an `onClick`, check for: a matching `onKeyDown` (or the framework's keyboard-equivalent) handling at minimum Enter and Space the way a native `<button>` would; `tabIndex={0}` so it's reachable by keyboard at all; and an appropriate `role` (`button`, `link`, etc.) so assistive tech announces what it is. If a native `<button>`/`<a>` would work instead, that's the simpler fix — name it as the fix, not just the gap.
2. **New modals/dialogs/popovers**, check for all of: focus moves into the modal when it opens (usually to the first focusable element or a heading); focus is trapped inside while open (Tab/Shift+Tab don't escape to the page behind it); Escape closes it; focus returns to the element that opened it when it closes; `role="dialog"` (or `"alertdialog"` if it blocks on a decision) with `aria-modal="true"` and either `aria-labelledby` pointing at a visible heading or an `aria-label`. Missing focus-return-on-close is the single most commonly missed item of this list — it's invisible unless you specifically close the modal and check where focus landed.
3. **ARIA state kept in sync with actual state.** If a diff adds `aria-expanded`, `aria-selected`, `aria-checked`, `aria-current`, or similar, verify it's actually bound to the same state variable driving the visual change, not a separate hardcoded value that can drift the first time the component is refactored. An `aria-expanded="false"` on a visibly-expanded element is worse than no `aria-expanded` at all — it actively lies to assistive tech.
4. **Dynamic content that should announce itself.** Content that appears without a navigation/route change and should be noticed by a screen reader user (a validation error, a toast, a "results updated" message, a loading-to-loaded transition) needs `aria-live` (`polite` for most updates, `assertive` only for things that need immediate interruption) or to be placed where focus is already moving. A new inline error message with no `aria-live` region and no focus movement is silent to a screen reader user even though it's visually obvious.
5. **Images and icon-only controls.** A new `<img>` needs `alt` (empty `alt=""` only when the image is purely decorative and something else already labels the control). A new icon-only button (no visible text) needs `aria-label` — check specifically for buttons that only contain an SVG/icon with no accompanying text node.

## Severity framing for the report

- A non-native interactive element with no keyboard support is high severity — it's not a degraded experience, it's a task a keyboard-only or screen-reader user cannot complete at all, on the exact feature the PR just added.
- A modal missing focus trap or focus-return is medium-to-high — the feature works for a mouse user and silently breaks the moment someone tabs through it, which is exactly the kind of gap manual mouse-based testing during the PR's own development never surfaces.
- Drifted/hardcoded ARIA state is medium — it doesn't block the interaction, but it makes assistive tech actively report the wrong thing, which is worse for trust than reporting nothing.
