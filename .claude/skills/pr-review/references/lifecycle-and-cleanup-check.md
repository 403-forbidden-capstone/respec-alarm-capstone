# Lifecycle & cleanup check

Timers and event listeners without cleanup are consistently the single most common source of frontend memory leaks in real-world static-analysis studies — more common than any other leak pattern combined. They're also easy to miss in review because the code that *creates* the leak (the `setTimeout`, the `addEventListener`, the subscription) is the whole visible diff; the bug is the *absence* of a line that was never written, which nothing about reading the diff draws attention to. This file makes that absence something the review actively checks for, rather than something it only notices if it happens to already be looking.

## When to run this

Triggered whenever the diff adds or changes: a `useEffect`/`onMounted`/component-lifecycle hook that starts a timer, subscription, event listener, or async operation; a `setTimeout`/`setInterval` call; an `addEventListener` call (including on `window`/`document`, not just DOM refs); a WebSocket, EventSource, or other long-lived connection; an async function whose result updates component state after an `await`. **Also triggered when a diff takes two or more previously-separate async entry points (e.g. two existing effects, or an effect plus an event callback) and routes them through one newly-shared function** — even if no single effect is new, the refactor itself can introduce a race that never existed before (see item 5).

## How to check it

1. **Every `useEffect` (or equivalent) that starts something must be checked for a matching stop.** For each one, name what it starts (timer, listener, subscription, connection, in-flight request) and find the specific cleanup: `clearTimeout`/`clearInterval` for timers, `removeEventListener` for listeners (matching the exact same event name and options/capture flag used to add it — a mismatched options object silently fails to remove), an unsubscribe call for subscriptions, `.close()`/`.abort()` for connections/requests. No cleanup function at all when one is needed is the loudest version of this; a cleanup function that exists but forgets one of several things the effect started is the quieter, easier-to-miss version.
2. **Async state updates after unmount.** For any `await` inside an effect (or a `.then()` callback) that's followed by a `setState`/store update, check whether there's a guard against updating state after the component/effect instance is gone — an `alive` flag set false in the cleanup function, an `AbortController` whose signal is checked, or the fetch itself being aborted. Setting state on an unmounted component isn't usually a hard crash in modern React (it's a warning, not an error), but the update itself can still corrupt shared/global state (a cache, a store) even when the local component is long gone — check what the state update actually touches, not just whether the component survives it.
3. **Loading/error/empty completeness, not just the happy path.** For every async operation feeding a UI (fetch, mutation, subscription), verify the render logic actually branches on all the states that operation can be in — loading, success-with-data, success-but-empty, and error — not just "loading vs. has-data." A component that only checks `if (loading) ... else render(data)` and never handles `data` being an empty array or `error` being set will render something misleading (an empty list styled identically to "no results ever," or silently nothing at all) rather than something wrong-looking enough to get caught in manual testing.
4. **Cleanup ordering when multiple things are started in one effect.** If an effect starts more than one thing (a timer *and* a listener, e.g.), check that the cleanup function actually stops all of them, not just the first one added — it's common to write the cleanup for whichever was written first and forget to extend it when a second thing was added later in the same effect.
5. **Shared-function readiness races.** When a diff funnels multiple independent async sources into one shared function (a "place a pin" helper called from a geolocation callback, a click handler, *and* a search-result callback, say), check whether that shared function assumes some ref/state is already set up (a map instance, a DOM node, a loaded SDK) — and if so, whether *every* caller can actually guarantee that at the moment it fires. Incident (2026-08-29, PR #59): `placePick()` unconditionally shows a "confirm" UI state but only places a map marker `if (map && marker)`; a `useKakaoLoader` effect sets those refs once the map SDK finishes loading, and a `navigator.geolocation.getCurrentPosition` callback can resolve *before* that — same component, two async starts, no ordering guarantee between them. The confirm button appears with no marker ever placed (nothing re-runs `placePick` once the map becomes ready), silently defeating the exact "let the user see what they picked" guarantee the diff was written to add. Name each async source that can call into the shared function, and check the slowest-plausible one isn't assumed to always win the race.
6. **Effect-declaration-order dependency.** React runs a component's effects in the order they're *declared in the source*, top-to-bottom, within a single post-render flush — when effect B's body reads a ref/value that only effect A's body sets, and both fire in the same flush (e.g. both depend on the same state that just changed), B must be declared *after* A, or B silently runs against A's not-yet-set value and never gets another chance to re-run if nothing else changes. Incident (2026-08-30, PR #59's fix commit `fb3421a`): the very race in item 5 above was "fixed" by splitting `placePick` into a `[picked, loaded]` marker-drawing effect — but that effect was declared *before* the pre-existing map-creation `[loaded, region]` effect in the file. When `loaded` flips true with `picked` already set, the drawing effect runs first (map/marker refs still null → bails), then the creation effect runs and sets the refs but never retroactively draws the marker — the exact same user-visible bug, reintroduced by the very fix meant to close it. When reviewing a diff that splits one effect into two to fix a race, check the *declared order* of the two new effects against what each one needs from the other, not just that both now exist.

## Severity framing for the report

- A genuinely leaking timer/listener/subscription on a component that mounts and unmounts repeatedly during normal use (a modal, a tab, a list item) is medium-to-high — it degrades over a session rather than failing any single test, which is exactly why it reaches production undetected.
- A missing loading/error/empty branch is medium severity on its own but escalates to high if the silently-wrong render could be mistaken for a correct empty/zero state by a real user (e.g., "0 results" indistinguishable from "still loading" or "request failed").
- State updates after unmount that touch shared/global state (not just local component state) are worth flagging distinctly and at higher severity than the "just a console warning" framing suggests, since the actual damage (a stale value overwriting a fresher one in a store or cache) can outlive the warning by a long time.
